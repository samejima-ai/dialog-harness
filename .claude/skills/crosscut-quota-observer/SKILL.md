# Quota Observer（共有枠の観測）

供給元アカウントの共有枠を観測し、異常パターンと閾値超過を**検出するだけ**の横断機構。

## なぜ必要か

DH には供給元アカウントの枠残量を観測する経路が無かった。2026-09-11 に判明した事実：

- 1 つのプロジェクトが **日次書込枠の 53% を単体で消費**していた
- その枠は **アカウント単位で共有**されており、超過すると同一アカウントの**全プロジェクトが停止**する
- これを見つけたのは人間が手で API を叩いたときで、**機構は何も知らせていなかった**

量産するほど、気づかないうちに枠が埋まる。本 skill はこの検出を人間の目から機構へ移す。

## 原則

- **判定を持たない**（`upgrade-spec-v6.19.0` I-6）。検出して数えるだけ。自動で昇格・停止・削除をしない
- **共有枠は cross-project state**（同 I-2）。per-project の宣言（REGIME.md 等）に書かない。
  枠は「そのプロジェクトの属性」ではなく「アカウントの状態」である
- **供給元非依存**（同 I-1 / Level A checklist A-3）。固有 API はアダプタに閉じ、本体は正規化 JSON を見る
- **数値は観測記録であって規範ではない**（同 I-3）。枠の値はアダプタに観測日付つきで置き、本体に焼き込まない
- **常時発火する検知を作らない**（同 I-7）。閾値は定常状態で 0 件になる値に置く
- **不在でも DH は動く**（同 I-5）。degrade は機能停止ではない

## 起動条件

| 契機 | 内容 |
|---|---|
| L0 対話 | 新規ツールの立ち上げ時に現在の枠消費率を提示する |
| 量産フェーズ | 定期確認（「あと何個作れるか」の判断材料） |
| 人間の明示 | 「枠の残量を見て」「書き込みが多すぎないか」等 |

**非起動**: 供給元アカウントを持たないプロジェクト（ローカル完結 / 組込 DB のみ）。

## 処理フロー

```
1. アダプタ選択（references/adapters/<provider>.md）
2. アダプタの手順で観測データを取得し、正規化 JSON に変換
3. scripts/quota-observer.py に渡して検出
4. 検出結果を提示（判定はしない）
5. 是正の要否は人間または L0 が決める
```

### 1〜2. 取得と正規化

供給元ごとの取得手順は `references/adapters/` を参照する。現在のアダプタ：

| provider | アダプタ | 状態 |
|---|---|---|
| Cloudflare | `references/adapters/cloudflare.md` | 実装済み（2026-09-11 観測） |

アダプタは**正規化 JSON** を出力する。スキーマは `scripts/quota-observer.py` の docstring が正本。
要点は「limits（枠の上限）」「resources（個数と容量）」「daily（日次消費）」の 3 つ。

### 3. 検出

```bash
python3 scripts/quota-observer.py --input observation.json
cat observation.json | python3 scripts/quota-observer.py --json
```

検出するもの：

| パターン | 意味 |
|---|---|
| `write_exceeds_read` | 読んだ行数より書いた行数が多い。差分更新ではなく**全件書き直し**の signature |
| `flat_daily_writes` | 日次書込がほぼ一定。利用者数に連動しない**定期バッチ**の形 |
| `threshold_databases` | 個数が上限に接近。1 ツール = 1 DB 運用では最も早く来る律速 |
| `threshold_rows_written` / `_rows_read` / `_kv_writes` | 日次の**共有枠**が閾値を連続超過 |
| `threshold_size` | 単一リソースの容量が上限に接近 |

上 2 つが重なったら全件同期バッチの確度が高い。これが 2026-09-11 の実測挙動そのもの。

**exit code は常に 0**（検出は FAIL ではない）。CI から呼んで赤くしたい場合のみ `--strict`。

### 4〜5. 提示と是正

検出結果は人間に提示する。**「だから昇格すべき」「だから削除すべき」は書かない**（I-6）。
是正の選択肢（書込の差分化 / 有料プランへの昇格 / 案件の分離）は人間または L0 が判断する。

## degrade（I-5）

以下のいずれでも **DH は通常動作する**。観測不能は warn として可視化し、機能停止にしない。

- 供給元の MCP / API が未認証
- API に到達できない
- 本 skill 自体が配布先に無い
- アダプタが当該 provider に未対応

「枠が見えない」は「枠が空いている」ではない。**観測不能をそのまま伝える**こと。

## 検出力の実証

```bash
python3 scripts/test-quota-observer.py
```

24 項目。**陽性ケースの中核は 2026-09-11 の実測データ**（合成値ではない）で、
陰性ケースには削除後の実際のベースラインを使う。「実リポで 0 件」は検出器が空振りでも
同じ表示になるため、それだけでは動作の証拠にならない（v6.17.0 の規律）。

## 未充足項目（Level A 配布性 checklist / v6.19.0 F2 時点）

`dev-env-spec.md` §Level A 配布性評価 checklist に照らした申し送り。

- **A-3 stack 中立性**: 本体は供給元非依存だが、アダプタは固有 API 名を含む。
  外部連携 skill は構造上 A-3 を完全には満たせない（`crosscut-autonomous-drive` が
  GitHub に依存するのと同型）。**固有情報をアダプタ 1 ファイルに隔離**することで、
  本体の中立性と供給元交代への耐性を確保する形を採った
- **E-2 認証情報不要**: アダプタは供給元の認証を要求する。ただし認証不在は degrade であり、
  DH の動作条件ではない（I-5）
