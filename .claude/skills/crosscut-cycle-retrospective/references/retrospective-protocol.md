# cycle 振り返りプロトコル（R1–R4 詳細）

`crosscut-cycle-retrospective` の各 Phase の手順・チェックリスト。SKILL.md から
必要時にロードする（progressive disclosure ＝購読量保護）。

## 目次
- R1: 事実収集
- R2: 構造化振り返り（5 観点）
- R3: 改善提案の仕分け（可逆 / 規範）
- R4: SUMMARY 反映（自動）+ 規範提案の提示
- SUMMARY エントリの書式と代謝の作法
- 都合の良い自己評価を避けるためのガード

---

## R1: 事実収集

その cycle の**一次情報**から機械的に拾う（一次情報絶対主義。記憶や印象で書かない）。
拾う先の優先順:

1. **PR / commit**: 何を出荷したか（`git log`、PR 番号・title・merge 状態）。
   マージ確認は `git fetch origin <base>` の HEAD 遷移を正本とする（GitHub API は
   キャッシュ遅延あり）。
2. **DELIVERY.md / HANDOFF.md**（あれば）: 献上物・体制事後評価・未解決事項。
   既存の体制妥当性評価があれば**引用**（R4-4 で再実行しない）。
3. **検証結果**: tsc / lint / test / sensors / build / 独立レビュー / ブラウザ実動の
   実際の合否。「通ったはず」でなく実ログの結果を書く。
4. **COUNCIL-LOG**（あれば）: この cycle で発動した Council の判定・少数意見・
   implementer_consent。判定が実装に正しく反映されたか。
5. **詰まりの痕跡**: 自力修正ループの回数、手戻り、誤認して直した箇所、環境摩擦。
   transcript / メモ / エラーログから拾う。**これを省略しない**（R2-3 の材料）。

出力: 事実の箇条書き（評価はまだ付けない ＝ R2 で導出）。

---

## R2: 構造化振り返り（5 観点）

R1 の事実から、SKILL.md のテンプレート 5 観点を埋める。各観点の書き方:

### 1. 成果（事実）
R1-1〜3 をそのまま要約。PR 番号・主要ファイル・検証結果。誇張しない。

### 2. うまくいったこと
機能した規律・判断・順序を挙げ、**なぜ効いたか**まで書く（次も再現するため）。
例:「一次情報を先に確認 → 推測で材料容量を決め打たずに済んだ」のように、
効いた理由を明示。理由なき「うまくいった」は学びにならない。

### 3. 反省・詰まり
バグ・手戻り・摩擦・誤認を挙げ、**なぜ起きたか**を書く。
- 都合よく薄めない（「軽微だった」で流さない）
- 同じ詰まりが過去 cycle でも起きていないか（SUMMARY を照合）。再発なら「再発」と明記
- 環境摩擦（worktree の env 不在等）も記録（次の人が踏まないため）

### 4. 体制妥当性（既存 L1 事後評価を内包）
`delivery-format.md` §体制妥当性の自己評価のチェックリストを適用:
- 判定モード（M1/M2/L2）は 過剰 / 妥当 / 過少 だったか
- 過剰の兆候: 独立レビューが何も指摘しなかった / 修正ループ 0 回 / 検証が実装を大きく超過
- 過少の兆候: 修正ループが上限到達 / 未解決 2 件以上 / context 圧迫
- Council 発動の要否・回数は妥当だったか
DELIVERY.md に既評価があれば引用し、無ければここで評価する。

### 5. 改善提案（R3 へ渡す）
2〜4 から導いた「次への改善」を列挙。この時点では未仕分け。R3 で分類する。

---

## R3: 改善提案の仕分け（可逆 / 規範）

R2-5 の各提案を**可逆性**で 2 分類する（DH v6 委譲モデル、SKILL.md 設計原則 2）:

- **[自動反映]**: `history/SUMMARY.md` に残す学び・事実。PR diff で可視化され
  revert 可能。次 cycle の F1 が読む。→ R4 で自動追記。
- **[提案のみ]**: SPEC / DONT / CLAUDE / 罠カタログ / RL / センサー等の**規範変更**。
  「何を禁じるか / どう作るか」の線引きゆえ人間承認必須。→ R4 で提示のみ、書き込まない。

判断が曖昧な提案は **[提案のみ]** へ倒す（fail-safe）。
「これは罠として追加すべき」「SPEC のこの記述を直すべき」は必ず [提案のみ]。
「今回こういう順序が効いた / こういう摩擦があった」は [自動反映]。

---

## R4: SUMMARY 反映（自動）+ 規範提案の提示

### 4-1. SUMMARY 自動反映（[自動反映] 分）

`history/SUMMARY.md` の「最終更新」節の**先頭**に、この cycle の振り返りエントリを
1 bullet 追記する（下記書式）。同時に**代謝**（最古 bullet を COLD へ送る）を、
プロジェクトの代謝ルールが定める保持件数に従って行う。

**代謝の作法**（reindex-librarian の情報代謝と整合、本 skill は追記 + 軽い代謝まで）:
- プロジェクトの SUMMARY 冒頭に代謝ルール（例「直近 N cycle 分のみ保持、N+1 件目
  追記時に最古 bullet を `history/COLD/…ARCHIVE.md` の先頭へ移す」）があれば**それに従う**。
- COLD は archive であって delete ではない（新しい順維持・無削除）。
- 本 skill は「追記 + ルール通りの 1 件押し出し」まで。HOT budget 超過の**本格的な
  再圧縮・叡智結晶化は reindex-librarian に委ねる**（下流依存、二重処理しない）。

### 4-2. 規範提案の提示（[提案のみ] 分）

[提案のみ] の各提案を、人間が採否を判断できる形で提示する:
- 提案内容（何をどう変えるか）
- 根拠（今回の cycle でなぜそう思ったか＝一次情報）
- 影響範囲（どの規範ファイルのどこか）
本 skill はここで**書き込まない**。採用されたら次 cycle の spec-architect（L0）が
枠内改変 or 枠新設として反映する。規範提案が複数で拮抗・不可逆なら Council に諮る。

### 4-3. 出力

対話には 5 観点の振り返りサマリと [提案のみ] リストを提示。SUMMARY には
[自動反映] エントリを書き込む。

---

## SUMMARY エントリの書式

プロジェクトの既存 SUMMARY の書式に**合わせる**（各プロジェクトで異なる）。共通の芯:

```
- YYYY-MM-DD（cycle **<ID>** <モード> <起点の一言>）: <成果 1〜2 文>。
  **うまくいった**: <効いた規律とその理由>。**反省**: <詰まりとなぜ>。
  **体制**: <M1/M2/L2 = 過剰/妥当/過少>。**改善提案（人間承認待ち）**: <規範提案があれば>。
  儀式レベル <n>、<モード>維持。P3 = <残作業>。
```

既存エントリ（他 cycle の bullet）の粒度・語彙・絵文字の有無に倣うこと
（SUMMARY は F1 が毎回読む＝書式の一貫性が購読効率を守る）。

## 都合の良い自己評価を避けるためのガード

自己評価は「うまくいった」に寄りやすい（実装した本人が振り返るため）。以下を守る:

- **反省・詰まりを空にしない**: 完璧な cycle はほぼ無い。修正ループ・手戻り・誤認・
  環境摩擦のどれかは必ずあったはず。R1-5 で拾った詰まりを R2-3 に必ず反映する。
- **検証結果は実ログで**: 「通ったはず」「動くはず」は書かない。実際の合否のみ。
- **再発を隠さない**: 過去 cycle と同じ詰まりなら「再発」と明記（SUMMARY 照合）。
  再発は「学びが定着していない」シグナルで、規範提案（[提案のみ]）の有力候補。
- **少数意見・保留を保持**: Council 少数意見や「保留にしたもの」を残作業に残す
  （消さない）。次 cycle が拾えるように。
- **独立性が要るなら別視点で**: 重要 cycle は、振り返りを実装コンテキストから隔離した
  fresh subagent に一次情報だけ渡して回すと、自己評価バイアスが減る（任意）。
