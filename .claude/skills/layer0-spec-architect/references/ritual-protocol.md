# 振り返り儀式プロトコル

L0（spec-architect）が対話開始時に実行する「過去文脈⇔現欲求」照合プロトコル。
1→5運用で履歴層を活用し、認識ズレ・車輪の再発明・訂正漏れを防ぐ。

---

## 設計原則

- **対話コスト最小化**: 儀式は必要最小限に。無駄な質問は一切しない
- **人間は気付き役、AI は検出・提示・記録役**: 人間にできないことを AI が担う
- **曖昧応答は AI 充当**: 「どうでもいい」シグナルと解釈し、推定値で埋める
- **儀式拒否は尊重**: 人間欲求を優先し、代わりに AI が背景で照合を回す
- **形骸化防止**: 儀式自体を履歴化して効果測定する

---

## 儀式レベル（4段階）

| レベル | 条件 | 処理 | コスト目安 |
|---|---|---|---|
| 0 | `history/` なし、または前回ループから経過なし | 完全スキップ | ゼロ |
| 1 | 30日以内、規模変化なし、LC=1 | SUMMARY.md のみ読込、1問確認 | 〜30秒 |
| 2 | 30日超 or 機能追加・変更を含む対話 | SUMMARY + 関連 INTENT、2〜3問 | 〜3分 |
| 3 | LC=2 保守 or 90日超 or 規模変動±2以上 | history/ 全層読込、5〜10問 | 〜15分 |

### ベースレベル判定フロー

```
1. history/ 存在確認
   なし → レベル 0
2. LC 判定（regime-assessment.md のロジックに従う）
   LC=0 → レベル 0
   LC=2 or 最終献上から 90日超 → レベル 3
3. 対話冒頭の発話内容を軽く解析
   機能追加/変更/廃止の示唆あり → レベル 2
   バグ修正のみ → レベル 1
   規模変動 ±2 以上の示唆 → レベル 3
4. 上記で決まらない場合 → レベル 1（デフォルト）
```

## 動的格上げ

儀式実行中に以下を検出した場合、その場で一段階格上げ。

| 検出シグナル | 格上げ |
|---|---|
| 過去 INTENT と矛盾する欲求 | 1→2 |
| 廃止機能の復活要求 | 1→2 |
| 却下済み案の再提案 | 1→2 |
| 大規模リファクタの示唆 | 2→3 |
| 規模判定が L2 閾値接近 | 強制 3 |
| 訂正カスケード検出（1訂正が複数機能に波及） | +1 |

## 動的格下げ

以下を検出したら一段階格下げ。対話コスト最小化を優先。

| 検出シグナル | 格下げ |
|---|---|
| `history/` がほぼ空（INTENT 3件以下） | 2→1 |
| 人間が明確に「軽くやりたい」と発話 | 2→1 |
| 純粋なバグ修正のみで仕様変更なし | 1→0 |
| **曖昧応答が2回連続**（E1対応） | 現レベル −1 |

曖昧応答 2回連続は「記憶が薄い領域＝重要度低」のシグナルと解釈し、深掘りを自動停止する。

## 儀式の3フェーズ（実行時）

レベル 1 以上で実行。各フェーズはレベルに応じて深度が変わる。

### F1: 過去文脈サマリ提示（AI主導・質問なし）

1. SUMMARY.md の鮮度判定
   - `SUMMARY.md` 最終更新日 < `history/` 内他ファイル最新更新日 なら再生成
   - 一致なら使い回し（詳細は `history-layer-spec.md` のSUMMARY自動生成トリガー）
2. レベルに応じた履歴ロード（**情報代謝 tier に従い購読量を抑える**・v5.19.0）
   - レベル 1: SUMMARY.md のみ（HOT 結晶層）
   - レベル 2: SUMMARY（HOT）+ 対話話題に関連する INTENT 項目（関連 WARM・AI が関連性フィルタで選別）
   - レベル 3: SUMMARY（HOT）+ 関連 INTENT + CHANGELOG 直近10件 + REGIME-LOG 直近5件（関連 WARM）
   - **COLD（`history/archive/`）は既定でロードしない**（retrievable・必要時のみ明示 retrieve）。レベル 3 でも全 INTENT の生ロードは避け、結晶化済み HOT + 関連 WARM に絞る
   - 趣旨: F1 の入力を全 history から HOT + 関連 WARM に絞ることで読み込みコスト（AI 購読量）を激減させる（情報代謝サイクルの「最小の第一歩」。tier 定義は layer0-reindex-librarian/references/metabolism-regime.md）
3. 人間に**1問だけ**提示: 「前回ここまで進みました。今回はこれの続きで合ってますか？」
4. **CTL 同期（v6.1.0・儀式の発火主体）**: `scripts/council-log-sync.py` が存在すれば
   `python3 scripts/council-log-sync.py sync --prune --recompute` を走らせる（COUNCIL-LOG →
   council-data 導出 + 孤児掃除 + CTL 再計算）。これが CTL 記録経路の主たる発火点であり、
   手順書依存に戻さないための実行経路接続（`crosscut-council/SKILL.md` §CTL 記録 /
   `dh-upgrades/upgrade-spec-v6.1.0.md`）。スクリプト不在なら skip（利用者プロジェクトで壊れない）。
   同期は読取専用の導出で可逆・低コスト。質問は挟まない（F1 は質問なしフェーズ）。
5. **軸独立性・観測バイアス監査（v6.6.0）**: `scripts/council-axis-audit.py` が存在すれば
   `python3 scripts/council-axis-audit.py` を走らせ、出力の「総括」節だけを読む
   （スクリプト不在なら skip）。CTL 同期と同様に**読取専用の集計**であり、質問は挟まない。

   warn が出た場合の扱い：

   | warn | 意味 | 還流先 |
   |---|---|---|
   | 軸冗長の疑い（`stance` 一致率 **と** `dimension` Jaccard の両方が閾値超え） | 観測次元が重複している＝軸の再設計対象 | **F3 で人間に予告**（軸の増減は L0 対話 + 人間承認） |
   | confidence 固定の疑い（軸内 σ < 0.10） | 議題ではなく役柄を採点している | persona prompt に軸固有の帯が書かれていないか点検（`crosscut-council/references/personas/business/README.md` §編集プロトコル） |
   | 実効配分が系統的に有利な軸あり | confidence が第二の重みとして働き宣言配分を歪めている | **F3 で人間に予告**（`council-weights.md` の数値是正は L0/D5 専管） |
   | `situational_modifier` の合計 0 宣言違反 | 重み表そのものの不整合 | 同上 |
   | `dimension` 記録率 < 50% | 冗長判定の分解能不足 | Council 発動側に `dimension` 記録を促す（`output-format.md` §8 で必須と規定済み） |

   **本監査は LLM 判定を含まない**（集計のみ）。軸のバイアスを LLM に検査させると検査側が
   同じ死角を共有するため、判定は人間に残す
   （`delivery/ANALYSIS-council-axis-independence-2026-07-26.md` §3-1）。
   したがって warn は**検出の報告**であり、是正の実行を含まない。

### F2: 認識ズレ検出（AI主導・検出時のみ質問）

1. 新欲求 × 過去 INTENT の照合
2. 以下のパターンを AI が自動検出:
   - 矛盾: 過去の条件と両立しない欲求
   - 復活要求: 廃止機能の機能復活を示唆
   - 再提案: 却下案リストに載っている案の再提案
3. 検出時のみ人間に確認:
   - 矛盾 → 「F001 の『上限 30 品』と今の『上限なし』は両立しないです。どちらを優先？」
   - 復活要求 → 「F003 は 2026-03-20 に利用率低で廃止しました。復活条件を満たしますか？」
   - 再提案 → 「上限なし案は当初『パフォーマンス劣化リスク』で却下しました。状況変化ありますか？」
4. 検出なしなら**質問なし**でF3へ

### F2.5: CTL 事後評価（v6.1.0・「問う契機」の必須経路）

CTL（Council Trust Level）昇格の律速は record ではなく**事後評価**（agreement_rate を
作る唯一の燃料）。記録が満ちても事後評価が回らねば CTL は上がらない。哲学者の第3の道
（Council `council-2026-07-01T-ctlrec1`）に基づき、儀式が「この委譲は妥当だったか」を
**問う契機**を保証する。CTL の値ではなく「問う契機」を機構が担う設計。

1. F1 ステップ 4 の同期後、`python3 scripts/council-ctl.py pending` で未評価判定を列挙する
   （スクリプト不在なら本ステップ skip）。
2. 未評価があれば人間に**まとめて 1 問**で問う: 「前回以降の Council 判定 N 件が未評価です。
   それぞれ推奨どおり採用しましたか？（一括 agreed / 個別に確認 / 後で）」
3. 回答に従い `council-ctl.py evaluate <id> --status agreed|modified|rejected` を実行する。
   - 「後で」を選んだ場合は評価を保留（pending のまま）。強制しない（惰性で agreed を
     押させない — 事後評価の意識的契機を守る）。
   - `rejected` が出たら rate が下がり CTL 降格しうる（`ctl-maturity-strategy.md` §退行）。
     これは正しい挙動（委譲が妥当でなかった事実を CTL に反映する）。
4. 未評価なしなら**質問なし**でF3へ。

**レベル別の深度**: レベル 1 は「一括 agreed / 後で」の 2 択軽量版。レベル 2/3 は個別確認を
推奨（judgment ログをレビューして decision_category 別の傾向も見る）。本ステップは
`scripts/council-ctl.py` 不在の利用者プロジェクトでは完全 skip（後方互換）。

### F2.6: 時限規範の再審（review_trigger 発火列挙・2026-08 追加）

「足す機構」と同格の「減らす・時限化する機構」の実行経路（Council `council-2026-08-05T14:34:36Z-f5fc45`
メタ診断への応答。設計材料: `delivery/ANALYSIS-norm-lifecycle-metabolism-2026-08-05.md`）。
新しい常駐機構は作らず、既存の儀式に寄生する。

1. **`scripts/norm-scan.py` を走らせる**（v6.13.0 F5 / v6.18.0 C-1 で着地）。存在すれば
   `python3 scripts/norm-scan.py` を実行し、出力の「発火」節を読む（スクリプト不在なら
   従来どおり手動 grep にフォールバック。利用者プロジェクトで壊れない）。
   **本走査器は LLM 判定を含まない機械列挙**であり、判定は持たない（同 F5-3）。
   > 手順書に「grep で収集する」と書くだけでは実行主体が無く空文化する。
   > v6.1.0 の CTL 記録が同じ形で死んだ（発動 53 回に対し記録 1 件）。走査器はその再演を避ける配線である。
2. 発火判定は走査器が行う: `date:`（期限超過）/ `cycles: N`（N cycle 相当の経過・日数近似）/
   `stage_transition: Sx→Sy`（REGIME の lifecycle_stage が Sy に到達）/
   `model_generation`（model-recommendations.md が当該規範より新しい）。
   **`measured: <条件>` は機械判定しない** — 条件が自然文であり LLM 判定を要するため、
   列挙して人に見せるに留める（I-3 検知は決定論）。
   走査器は**未発火・判定不能も記録する**（黙って捨てない）。「発火 0 件」が空振りでないことを
   出力の内訳（総トリガ数 = 発火 + 未発火 + 判定しない）で確かめられる。
3. 発火ありなら人間に**まとめて 1 問**: 「時限規範 N 件が再審期です。残す / 降格 / 廃止？
   （一括残す / 個別に確認 / 後で）」。「後で」は保留可（強制しない）。
4. **非対称原則**: 降格・廃止は軽い手続き（本ステップの一言承認）で実行してよい —
   追加側の重い手続き（Council・純化 RL 判定）を削除側に課さない（重くすると減らす機構が使われず死ぬ）。
   例外: **予防型規範**（踏み外すと本番事故）の廃止だけは慎重側に倒し、拮抗すれば Council に諮る。
5. 該当なし・メタデータ未使用のプロジェクトでは**完全 skip**（質問なし・後方互換）。

### F2.7: 開発環境評価の定期再実行（v6.15.0 F5・2026-08 追加）

DH 本体（メタハーネス開発）に限る。展開プロジェクトでは skip。

1. 前回の環境評価（`delivery/DIAGNOSIS-*` — ループ 6 軸 / グラフ 10 特徴 / 成熟度 8 段階の採点）
   から **四半期経過**、または **major 昇格の前**であれば、再評価を人間に提案する。
2. 再評価は前回と同じ外部規格に照らし、**前回値との差分**（B− → 今回、成熟度 3/8 → 今回）を
   必須出力とする。差分の無い再評価は出力を省略してよい（形骸化防止・TR-4 と同旨）。
3. 工程カタログの一次材料（`delivery/ANALYSIS-agentic-sdlc-world-standard-*`）も同周期で
   再調査候補に挙げる（この領域の陳腐化速度を考慮し 6 ヶ月目安・v6.15.0 F5-2）。
4. 提案に対する採否は人間が決める（強制しない。「後で」保留可 — F2.6 と同じ非強制原則）。

### F3: 履歴更新予告（人間は承認のみ）

1. 対話で確定した更新内容を AI が**通知形式**で宣言
   - 「以下を INTENT.md に追加します」
   - 「F001 の条件を v2 に更新します」
   - 「R=2（他人配布）のため REGIME.md の R スコアを +1 更新します」
2. 人間が承認 or 修正指摘
3. 修正指摘ありなら該当部分のみ修正して再提示

**重要**: 履歴の実際の書き込みは L1 の献上タイミングで行う（`layer1-autonomous-dev/references/delivery-format.md` の「履歴層更新差分」セクション参照）。F3 はあくまで「予告」。

## E1対応: 曖昧応答の扱い

儀式中に曖昧応答（「たぶん」「どうだったかな」「どっちでもいい」等）が返った場合の処理。

### 基本方針

曖昧応答 = **「AI が良きに計らえ」シグナル**と解釈する。質問を重ねず、AI が最適解で充当する。

### A: AI充当 + 通知型（常時適用）

1. AI が過去 INTENT・CHANGELOG・状況データから最適解を選択
2. 「〇〇と推定しました。違ったら次回教えてください」と**通知のみ**（再質問しない）
3. 対象項目に `**確度**: AI推定 (YYYY-MM-DD)` メタデータを付与
4. SUMMARY.md の「要再確認リスト」に追加
5. 次ループの F2 で「AI 推定項目に異議ないか」を**1問にまとめて**一括確認

### C: 儀式軽量化（併用）

曖昧応答が **2回連続**発生したら、儀式レベルを自動 −1 格下げ。

- 記憶が薄い領域＝重要度低の推定として深掘りを停止
- 格下げ後も F1/F2 の検出は継続（ただしより簡略化）

## E2対応: 儀式拒否への対応

「儀式いらない、すぐ作って」等の拒否発話を検出した場合の処理。

### 基本方針

儀式拒否 = **「今すぐ作りたい」欲求の優先表明**。拒否は全面受容。代わりに AI が **L1 実装中に背景で履歴照合を回す**（人間にできないことを AI が担う）。

### 実行手順

1. 儀式を完全スキップ（F1/F2/F3 全て省略）
2. REGIME-LOG.md に「儀式拒否: 第N回」を記録
3. L1 起動時に以下を暗黙の追加タスクとして引き渡す:
   - 過去 INTENT との整合性チェック（実装完了後）
   - 廃止機能への回帰検出
   - 却下案の再実装検出
4. 矛盾検出時のみ `DELIVERY.md` の「履歴整合性チェック」セクションで報告（人間に質問はしない、報告のみ）

### 連続警告

拒否が **5回連続**したら、SUMMARY.md の「注意事項」セクションに以下を**常設表示**:

```
⚠ 直近5回儀式スキップ、認識ズレ蓄積の可能性
```

- 強制介入はしない（人間裁量を最終尊重）
- 警告解除条件: 1回でも儀式を実施すれば即解除

連続回数は REGIME-LOG.md の「儀式拒否」フィールドで追跡。

## 形骸化防止メカニズム

儀式自体が形骸化しないよう、以下を組み込む。

### 1. 儀式実行ログ

CHANGELOG.md の「儀式記録」セクションに毎回追記（`history-layer-spec.md` のCHANGELOGテンプレ参照）。

- レベル（動的格上げ/格下げの履歴も含む）
- スキップの有無
- 検出件数（矛盾/復活/再提案）

### 2. スキップ連続警告

儀式スキップが **5回連続**で SUMMARY.md に警告常設（E2対応と同じ閾値）。

### 3. 儀式効果の事後評価

L1 の「体制事後評価」（`delivery-format.md`）に以下を追加記録:

- 儀式で検出された件数
- 検出により回避された手戻り（推定）
- 儀式時間 vs 実装時間の比率

連続して「検出ゼロ」が続く場合は REGIME-LOG.md に警告し、次回レベル判定を一段下げ検討。

## 儀式と L0 本来フロー（対話・モード判定）の接続

`SKILL.md` の処理フローでは、ステップ 2（対話による具体化）の**前**に儀式を実行する。

```
1. イメージ受領
1.5. 振り返り儀式（LC 判定 → レベル判定 → F1〜F3 実行）  ← 本プロトコル
2. 対話による具体化（儀式で得た過去文脈を前提に進行）
3. ドキュメント化
4. モード判定
5. 人間レビュー
6. 開発環境構築
7. 出力
```

新規プロジェクト（LC=0）では儀式レベル 0 により完全スキップ。0→1 開発には一切のオーバーヘッドが発生しない。
