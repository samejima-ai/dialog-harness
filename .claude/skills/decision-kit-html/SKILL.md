# Decision Kit HTML v3（1 項目ずつめくる判断キット + 全体の絵）

> v3 = 2026-11-18 出口を 2 本に分ける（本質問答 kit-deguchi-1118、upgrade-spec v6.22.0）。答えを全部合わせた「全体の絵」を見て、
> 揃っていれば実行に回し、ずれていればずれた所だけ詰めに回す。合言葉は「揃えてから任せる」「全体の絵で揃える」。
> v2.2 = 2026-10-26 現物は全体を俯瞰しつつ対象を強調（focus・box）。小さい絵を引き伸ばさない。
> v2.1 = 2026-10-26 確認の作業で「ある物は現物・無い物は様式（既定の様式・見本・レイアウト）」の画像を出す決まりを追加（target・template・file）。
> v2 = 2026-10-23 kakuman-platform の認識合わせキット kit-format-1023 の回答で決めた型（upgrade-spec v6.21.0）。
> v1（全部の問いを縦に並べ、事実・図・用語を多く出す型）は使わない。問いが多くても v2 以降の型で組む。

## 起動条件

「判断キットにして」「○×で答えたい」「質問して決めたい」「認識合わせして」「選ばせて」「解説も込で選ばせて」
「モックで認識合わせ」「回答をコピーできる形で」。判断点が 3 つ以上、または絵が無いと決められない時は明示が無くても使う
（2 つ以下で絵が要らない判断はチャット本文で聞く）。

## 最上位の規律 = 集中して理解 → 判断を素早く

1 画面に出すのは **1 項目だけ**。人は「何が困っていて（課題）、何が起きていて・どうするのか（説明）、何を決めるのか（質問）」を
読んで、**絵を見ながら**選ぶ。読む量は欄ごとの上限で絞り、細かい事実は「▸ 詳しく」に畳む（消さない）。

## 1 項目の形

| 場所 | 中身 | 上限（組み立てで超えたら知らせる） |
|---|---|---|
| 左（スマホは上） | **絵を必ず 1 枚以上**（無い項目は組み立てが止める） | — |
| 右 1 | 見出し（短い名詞） | 24 字 |
| 右 2 | **課題** = 何が困っているか | 120 字 |
| 右 3 | **説明** = いま何が起きている・どうするか（箇条） | 3 つ・各 90 字 |
| 右 4 | ▸ 詳しく（出所・細かい事実。任意） | — |
| 右 5 | **質問** = 決めること（動詞で終える 1 行） | 60 字 |
| 右 6 | **選択肢** = 2〜4 個、各 理由 1 行、AI推奨は 1 つ（灰の札） | 各 50 字・理由 60 字 |
| 右 7 | **メモ**（自由） | — |

- **複雑な項目は 2 枚に分ける**（`phases: true`）: 1 枚目 = 札「解説」（課題・説明・詳しく）、2 枚目 = 札「選ぶ」（質問・選択肢・メモ）。
  絵は両方に出す
- 選んだ案 = 紫の塗り、AI推奨 = 灰の札だけ（選んだ色と混ぜない）。選べない案は `disabled` で並べ、理由を `why` に
- キー: ← → でめくる、A〜D / 1〜4 で選ぶ。下の帯に 回答数・前へ・次へ・まとめをコピー

## 絵の決まり（現物 ＞ 様式 ＞ モック ＞ 挿絵 ＞ 表・グラフ）

| 種類 | 何か | いつ |
|---|---|---|
| **現物** `original` | もうある物の実物（図面・画面・帳票・Excel・Word・PDF・写真・スクショ。切り抜き・枠や数の描き足し可） | 問いが今ある物を指すとき。いちばん先 |
| **様式** `template` | まだ無い物の、既定の様式・見本・レイアウト（スキル同梱のテンプレ、会社の書式、過去の同じ種類の成果物）。`source` に出所 | これから作る物の形を確かめるとき |
| **モック** `mock` | 触れる見本（`html` を埋め込む / `url` で別の Artifact を開く。`src` に代わりの画像） | 操作や流れを決めるとき |
| **挿絵** `illustration` | 様式も無いとき AI が描く見本（キャプションに「見本」「AI が描いた」） | 書き方・形の違いを見せるとき |
| **表** `table` / **グラフ** `chart` | 見比べ・数 | 上の 4 つが無いときだけ |

### 確認の作業 = ある物は現物、無い物は様式を見せる

ファイル・帳票・画面・図面などを確かめる項目には `target` を付ける。文字の説明だけで確かめさせない。

| target | 先頭の絵 | 探す順 | 組み立て |
|---|---|---|---|
| `exists`（もうある） | **現物** | 添付 → 接続した Drive・PC のフォルダ → 前の成果物 | 現物以外が先頭なら止める |
| `new`（まだ無い） | **様式** | ① スキル同梱のテンプレ・見本（`templates/`・`assets/`）② 会社の既定の書式 ③ 過去の同じ種類の成果物 → 無ければ挿絵・モック | 現物が先頭なら止める |

- `file` に xlsx・docx・pptx・pdf・画像のパスを書けば、組み立てが `scripts/render_visual.py` で PNG にして埋め込む（`page` でページ、`trim` で余白の切り落とし。表計算は既定で切る、Word・PDF は紙面の割付を見せるため切らない）
- **現物は「全体を俯瞰 ＋ 対象を強調」で見せる**（対象だけの切り抜きにしない）。`focus` = 表計算のセル範囲（写しを黄で塗り赤の太枠。元のファイルは触らない）、
  `box` = どの種類でも [左, 上, 幅, 高さ]%（外を薄く暗くし赤枠）。どちらも無いと組み立てが知らせる（全体そのものが対象なら `whole: true`）。
  細部が要るときは、全体（強調つき）→ 対象の拡大 の順に 2 枚並べる。絵は元の大きさより拡大されず、押すと拡大
- 様式の中身は仮（〇〇・ダミー）でよい。見せるのは「形・並び・欄」。キャプションに「中身は仮」と書く
- 様式・挿絵は点線の枠で出る（現物と取り違えない）。現物にはファイル名、様式には出所が添えられる
- 現物も様式も見つからないときは、挿絵を描く前に「様式が無い」ことを `more` に書く（探した場所も）
- 現物を変える提案なら、現物（今）→ 挿絵・モック（変えた後）の順に 2 枚並べる
- 先頭の絵がいちばん大きく見える。より上の種類があるのに下の種類を先頭にすると組み立てが知らせる
- 本番の画面・図面・帳票の画像は repo に入れない（`file` で読んだ現物も公開版にだけ埋め込まれ、出るのはファイル名だけ）。spec には `{{IMG:name}}` を書き、`--images`（scratch の JSON）で公開版にだけ埋め込む

## 手順

1. **集める**: 判断点ごとに一次情報を実測（転記でなく実測、数字に出所）。起きている障害は問いにせず先に直す
2. **Council に先に回す**（技術の得失・作るか否か・時期・直し方）→ 判定を `rec` に。人に残すのは 委任の範囲 / 好み / 現場の知識
3. **項目に畳む**: 1 項目 = 1 判断。認識合わせなら 1 項目目を「この受け取り方で合っていますか」にする。
   **戻せて、人の感覚が効かない事は問いにしない**（AI が決め、実行報告に書く）。感覚が効く問い（形・言葉の意味・大事にする順番・現場の知識）と、
   提出物（社外の相手に届く物）に関わる問いには `"feel": true` を付ける（組み立ては読まない。扱いは下の「未回答の扱い」）
4. **絵を作る**: 確かめる物があるか先に調べて `target` を決める。ある → 現物（本番を読むだけで撮る・切り抜く・`file` で画像化）。
   無い → 様式（同梱テンプレ・既定の書式・過去の成果物を `file` で画像化）→ 無ければモック → 挿絵 → 表・グラフ
5. **spec を書く**（`references/spec-schema.md`）。`summaryTitle` / `summaryFooter` は**プロンプト**として書く（下）
6. **組む**: `python scripts/build_kit2.py <spec.json> <out.html> --images <images.json> --strict`
   （絵の無い項目・target と先頭の絵の食い違い・上限を超えた文字・推奨の無い問いで止まる）。PC 1440 と スマホ 390 で横にはみ出さないかを
   `NODE_PATH=$(npm root -g) node scripts/check_layout.js <kit.html> <dir>` で見る（全項目とまとめを明 / 暗で撮る。node が無い環境では目で見る）
7. **渡す**: その案件の「キット用の 1 本」（決定記録に URL がある）に**上書き**して公開する。新しい Artifact は作らない。
   キット用の 1 本がまだ無い案件だけ 1 本作り、URL を決定記録に書く。前のキットに未回答が残っている間は上書きせず、先に聞く。
   spec と Markdown 正本はプロジェクトの記録の置き場へ
8. **回答が返ったら、まず全体の絵**（下の「出口 = 全体の絵 → 2 本に分かれる」）。実行は全体の絵に「これで実行」が返ってから。
   `feel` の問いが 1 つも無いキットだけは、全体の絵を飛ばして実行に回す。
   決定記録（決定・理由・捨てた案・出どころ）を正本に残し、出荷したら PR 番号つきの実態に直す
9. **報告 = 照合報告（`shougou-houkoku`）**: 全体の絵（約束）と出来た物を本文の一枚で並べ、違う所に印を付け、「直す物はどれか」だけ聞く。
   違いが無ければ「約束どおり」の一行で終える。ずれと原因の札は決定記録の実行結果に足す。報告用の Artifact は作らない

## 出口 = 全体の絵 → 2 本に分かれる（v3）

本質 = **揃えてから任せる**。ずれは 1 問ずつの答えの中には無く、答えを全部合わせた時に出る（同じ言葉でも人と AI で頭に描く形が違う）。
だから回答の文面を読んで見抜こうとしない。合わせた形を絵で見せ、人が一目で決める。AI の役は 絵を描く ＋ 見る所に印を付ける。

### 流れ

1. キットのまとめ（答えの表 + プロンプト）を貼り戻してもらう。このプロンプトは「全体の絵を出して」で、まだ実行させない
2. AI が **全体の絵** を作る = 全部の答えを合わせた出来上がりの下書き。型は成果物の種類でなく **判断対象** で選ぶ（本質問答 zentai-e-kata-1118）:

   | 判断対象 | 例 | 主役の構図 |
   |---|---|---|
   | **見せ方** | チラシ・お知らせ・報告書・HP | 全体のレイアウトと、フォント・余白など細部まで本番に近い見本（様式に答えを入れる） |
   | **数と段取り** | 見積・数量・工程・出面 | 表・グラフ・図解で見比べる（どの答えがどの数字・日程に効くかを番号で結ぶ） |
   | **仕組み** | アプリの画面・スキルの流れ・データのつながり | 設計構造の図解・フロー図（画面が絡む時はモックを添える） |

   - **前 → 今の差分（どの型でも共通）**: 原本・前の版・前の見積がある時は、前（現物）と今（答えを合わせた下書き）を左右に並べ、変わった所に印を付ける。前が無い時だけ、今の 1 枚で出す
   - **判断対象が混ざる時**（例: 工程表をお知らせにして配る）: 問いの多い方の構図を主役にして 1 枚目、もう一方を 2 枚目に置く
   - 中身が仮なら「中身は仮」と書く
3. 絵の中の **言葉だけで決まった所** に印（黄の点線枠 ＋ 番号 ＋「言葉だけ」の札）を付ける = 選んだ案に絵が無かった／挿絵だけだった／
   メモの自由記述を絵にしていない／答え同士で形がぶつかる／`feel` の問いが未回答。印は多くて 5 つ（6 つ以上ならキットの畳み方が粗い合図）
4. 質問は 1 つだけ:「この出来上がりで合っていますか」
   - **A. これで実行**（推奨は付けない。人が見て決める）
   - **B. ここを詰める**（ずれている所を印の番号か言葉でメモ）
5. 出し方: 判断が 1 問なのでチャット本文に出す（インラインの図・モック ＋ この質問）。現物の画像が要る・大きい時だけ、キット用の 1 本に上書きして出す
6. A → 実行に回す（揃った所だけを実行）。B → 詰めに回す: ずれた所だけを次の周の判断キットにして、キット用の 1 本に上書き。
   揃った所は「変えない決定」にする。次の周に答えたら 1 に戻る

### 未回答の扱い

- `feel` の無い問いの未回答 = 推奨の案で進める
- `feel` の問いの未回答 = 推奨で進めない。全体の絵で印を付けて見てもらう
- メモが推奨と食い違う = 止めて聞かず、全体の絵で印を付けて見てもらう

### まとめのプロンプト（spec の summaryTitle / summaryFooter）

```
summaryTitle:
○○キット NNNN の回答です。まだ実行しないでください。全部の答えを合わせた出来上がりの全体の絵を出し、言葉だけで決まった所に印を付けて、「これで実行／ここを詰める」を聞いてください。

summaryFooter:
## 全体の絵のあと
- 「これで実行」→ この回答どおりに自律駆動で実行する。処理できるものを全て完了し、最後に照合報告（shougou-houkoku）で、全体の絵と出来た物を並べて報告し、決定記録に決定と実行結果（ずれ・原因の札）を足す
- 「ここを詰める」→ ずれた所だけを次の周の判断キットにして、キット用の 1 本に上書きする。揃った所は変えない

## 実行の規則
- 作業場所・1 件 = 1 PR・PR 前の検査・独立レビュー・マージ権限（「これで実行」が承認）・本番は読むだけ・安全判定に止められたら止まる
- feel の無い問いの未回答は推奨の案で進める。feel の問いの未回答と、推奨と食い違うメモは、全体の絵で印を付ける
- 変えない決定（前の周で決まったこと）

## 回答ごとにすること
- Kn A: …。B: …（選ばれなかった案も書く）

## 作る順番
① → ② → …
```

まとめのページは 答えの表（項目・答え・メモ）+ このプロンプト + コピーのボタン。コピーできない環境では本文を選択する。

`feel` の問いが 1 つも無いキットは、summaryTitle を v2 の形（「この回答どおりに自律駆動で実行してください。…最後に照合報告（shougou-houkoku）で報告してください」）にしてよい。

### 前後のスキル

本質問答で目的と手段を決める → 判断キット（全体の絵で 揃う ↔ 詰める をくり返す）→ 実行 → 照合報告（`shougou-houkoku`。約束と出来た物を本文の一枚で照らす）

## 運用の決まり（2026-11-11 artifact-unyou-1111）

本質 = **キットは使い捨て、決定は一生もの**。キットはその瞬間に判断するための道具で、残すのは決定記録だけ。

- **作る線**: 判断が 3 問以上、または絵・操作・現物が無いと決められない時だけキットにする。2 問以下で絵が要らない判断はチャット本文で聞く（現状 → 分岐 → 選択肢）
- **数を増やさない**: 案件ごとのキット用 1 本に上書きする
- **決定記録の置き場**: 開発 = リポジトリの記録ファイル。現場・個人 = Google ドライブ「決定記録」フォルダの案件ごとのドキュメント 1 本。書くのは 決定・理由・捨てた案・出どころ・実行結果
- **上書き・削除の前に**: 答えが決定記録に写っていることを確かめる。写っていなければ触らない
- **人が見るのは実行報告だけ**。決定記録は AI が次のセッションで読むための物

## 混同しない

- 判断を確定させるのは人。キットは「決めるための面」を作るだけ（Council / spec-architect の代わりではない）
- 障害を問いにしない。好みと権限を AI が決めない。技術の比較を人にやらせない
- 詳しい情報を消して軽くしない。**畳んで**軽くする。絵は畳まない
