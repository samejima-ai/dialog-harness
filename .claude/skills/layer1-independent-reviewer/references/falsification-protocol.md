# Falsification Protocol — 反証指向の独立検証（v6.9.0 新設）

> 本文書は `layer1-independent-reviewer` 処理フロー 5.10「反証チェック」の詳細プロトコル。
> SKILL.md が「いつ・どこで」を定め、本文書が「何を・どう・どこまで」を定める（単一情報源）。

---

## 0. なぜ確証だけでは足りないか

既存フロー 3-5（仕様合致・動作確認・使用確認）は**確証**である — SPEC と成果物が一致する
証拠を集める向きの検査。しかし AI が実装とテストの両方を生成する体制では、次の構造的問題が残る：

- **All Tests Passed ≠ Software is Correct**。テストの Green が示すのは「現在存在する
  テストへの適合」であり、それ以上ではない
- 実装者と検証者が同一の最適化ループに入ると、テスト（評価指標）自体が攻略対象になる
  （Reward Hacking と同型）。DH はコンテキスト隔離（ループ分離）でこれを部分的に防いでいるが、
  隔離された reviewer が**確証照合しかしない**なら、「テストが正しいものを見ているか」
  （Test Oracle の妥当性）には届かない
- 罠 C2（自己言及の罠）の一般化: L1 が自分で書いたテストを自分で「通った」と判定する
  バイアスは、E2E に限らずユニット/統合テストにも乗る

したがって reviewer は確証に加えて**反証** — 「この実装が間違っていることの証明の試み」 —
を明示的に課す。確証は「合っている証拠を探す」、反証は「壊れる入力・状態を探す」。
向きが逆の 2 検査が揃って初めて独立検証と呼べる。

## 1. 反証対象の選定（リスクベース・打ち切り基準込み）

反証は網羅ではなく**リスク集中**で行う。尽きない反証に無限のコストを払わないための規律：

| 対象 | 反証試行 | 根拠 |
|---|---|---|
| SPEC priority: **critical** の各機能 | **必須・各 1 件以上**（上限目安 3 件） | 壊れたときの被害が最大 |
| 状態を持つ操作（DB 書込・キュー・外部 API・リトライ・並行） | critical でなくとも 1 件推奨 | Oracle 不足が最も出やすい領域 |
| standard 以下の純関数的機能 | 任意（スキップ可） | コスト対効果で打ち切る |

打ち切り後も「やり残した反証」があれば §4 の「この PASS が保証しない範囲」に記載する。
**反証の省略は隠さず、保証範囲の外側として明示する**のが本プロトコルの中心規律。

## 2. 反証の 3 類型

### A. 挙動反証 — counterexample の構築

SPEC の記述から**壊れそうな入力・状態・順序**を導出し、実際に実行して確かめる。

- 境界値: SPEC「失敗 5 回で 15 分ロック」→ 4 回目 / 5 回目 / 6 回目、タイマー境界の直前直後
- 異常系: 空入力・型外入力・二重送信・途中切断
- 順序/並行: リトライ発生時の二重処理、同時要求での状態競合
- 導出元は **SPEC / DONT / sensors の記述のみ**（実装コードから「通りそうな入力」を
  逆算しない — それは確証の再生産であり反証にならない）

### B. テスト反証 — test-the-tests

既存テストが**そもそも落ちうるか**を検査する。Green を攻略しているテストの検出：

- **ミューテーション・スポットチェック**: critical 機能の実装 1 箇所を意図的に壊し、
  対応テストが FAIL することを確認して、**必ず原状復帰**する
  - 安全規約: 作業は一時的とし、復元後に `git status --porcelain` / `git diff` で
    成果物が clean であることを試行記録に含めて確認する（壊したまま献上する事故の防止）
  - **preserve 領域（archeo `no_modification`）では B 類型を実行しない**（一時的でも
    変更禁止と衝突する）。静的検査（下記）のみで代替する
- 静的検出: 恒真アサーション（`expect(true)`, 自明比較）/ **over-mock**（検証対象自体を
  mock しているテスト）/ expected 値を実装出力からコピーした自己整合テスト /
  アサーションなしの「実行するだけ」テスト

### C. Oracle 反証 — 観測点の十分性

テストの観測点が **SPEC の保証を観測できているか**を問う。テストを増やす検査ではなく、
既存テストの「見ている場所」を疑う検査：

- HTTP 200 だけ見て DB 状態・キュー状態・外部 API 呼出回数を見ていないか
- 「二重配信されない」系の保証に対し、配信の副作用（送信ログ・冪等キー）を観測しているか
- 観測点の不足は反証成立ではなく**提起**として記録（不足観測点の追加は L1 の責務）

### 5.5.2（E2E テスト妥当性検証）との関係

5.5.2 は E2E 限定の C1/C2/C3 検査（母集団トレース・構築規律・provenance）。本プロトコルの
B/C 類型はそれをユニット/統合テストへ一般化したもの。**E2E テストに対しては 5.5.2 の結果を
引用し、B/C 類型を重複実行しない**。

## 3. 認識論的注意 — 反証不成立は証明ではない

- 反証が全て不成立でも、それは「試した範囲で壊れなかった」以上を意味しない。
  記録は**何を試して壊れなかったかの有限の列挙**であり、正しさの証明ではない
- したがって PASS の意味は「確証チェック全通過 ∧ 試行した反証が全て不成立」に更新される。
  この有限性を毎回可視化するのが §4 の必須欄である

## 4. 出力規約 — VERIFICATION.md「反証記録」セクション

```markdown
### 反証記録

| 対象 | 類型 | 試行内容 | 結果 |
|---|---|---|---|
| F2 ログインロック (critical) | A | 5 回目失敗直後 + 15 分境界の前後で試行 | 反証不成立 |
| F2 ログインロック (critical) | B | ロック判定の閾値を 1 箇所改変 → tests/auth.spec FAIL 確認 → 復元（diff clean） | 反証不成立 |
| F4 通知配信 (critical) | C | テストは HTTP 200 のみ観測。二重配信保証に対しキュー状態の観測点なし | **提起**（Oracle 不足） |

#### この PASS が保証しない範囲（必須）

- 並行リトライ時の競合は単一プロセスでのみ試行（マルチプロセス未検証）
- F5 以下 standard 機能は反証試行なし（確証チェックのみ）
```

- **反証成立**（counterexample が SPEC 記載の保証を破る挙動を実証）→ **FAIL** として差戻し。
  訂正は書かず提起のみ（SKILL.md「訂正発見時の挙動」に従う）
- critical 機能で反証試行 0 件のまま PASS を返さない（検証不十分）。実行環境の制約等で
  試行不能な場合は、その理由を反証記録に明記した上で PASS（警告付き）とする
- 「この PASS が保証しない範囲」欄の省略はセンサー FAIL 扱い（DELIVERY.md 通過ゲート記録と
  同じ強制規約）
