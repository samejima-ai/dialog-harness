# CLAUDE.md — エージェント RL（Rules / Layer 規範）

このファイルは Layer 1 自律開発エージェント（および独立検証エージェント）が遵守する憲法。
**SPEC.md / DONT.md / REGIME.md と本ファイルが矛盾した場合、SPEC.md > DONT.md > REGIME.md > CLAUDE.md の優先順で従う。**

## 0. 大原則（最優先・絶対順守）

> **妹さんの絵を「不正解」と切り捨てない。**

これは UI 文言、効果音、配色、判定ロジックすべての最終チェックポイント。
コード書く時・テスト書く時・レビューする時、毎回この一行を思い出す。

## 1. 哲学 4 本柱（SPEC.md 参照、ここでは略記）

1. 絵 = 理解の証拠
2. 得意から伸ばす
3. 学習者ではなく救助者
4. 待ち時間も体験に変える

実装判断で迷ったら **「この実装は妹さんを救助者として尊重しているか？」** を問い直す。

## 2. 技術スタック

### 確定

| レイヤ | 採用技術 |
|---|---|
| 配信形態 | **Web PWA**（iPad Safari ターゲット） |
| ビルドツール | **Vite** |
| 言語 | **TypeScript（strict）** |
| UI フレームワーク | React or Solid（軽量優先、L1 が最終決定） |
| 描画エンジン | **HTML Canvas API**（Phase 1.0 は素の Canvas で十分） |
| ゲーム強化（必要時） | **Phaser.js** or **PixiJS**（待ち時間ミニゲーム / アニメで採否判断） |
| データ取得 | **Google Sheets API**（CSV エクスポート or `gviz/tq` 経由） |
| AI 判定 | **Gemini API（マルチモーダル）** — 無料枠優先 |
| ローカル保存 | **IndexedDB**（妹さんの絵）+ **localStorage**（設定） |
| テスト | **Vitest**（unit）+ **Playwright**（E2E） |
| リント | **Biome** or ESLint + Prettier |

### 検討余地（L1 判断委譲）

- 状態管理: Zustand / Jotai / 何も入れず React useState（Phase 1.0 は最後者推奨）
- スタイリング: CSS Modules / Tailwind / unocss（妹さんが触る部分は最小設計）
- PWA: vite-plugin-pwa

## 3. 検証方針（M2 標準）

### Shift Left 基盤 + 5 層エラー検出スタック

詳細: `../layer1-autonomous-dev/references/inferential-sensor-v2.md` を参照（共通 skill）。

`sensors/computational.md` 参照。要点:

- **TypeScript 型エラー 0**

- **Lighthouse PWA score ≥ 90**

### 推論的センサー（M2）

`sensors/inferential.md` 参照。要点:

- DONT.md の各禁則がコード / UI 文言 / 配色に反映されているか
- 「不正解」「✗」相当の表現が UI に存在しないか
- 描画 → 判定 → リアクションフローで「妹さんが追い詰められる」シーンが無いか

### 独立検証（layer1-independent-reviewer）

`sensors/review-checklist.md` を入力として、L1 献上後に独立検証を必ず実行する。
**M2 では実装完了直後の独立レビューが既定フロー**（明示指示なくても起動）。

## 4. 機能実装の優先順

```
1. F4 描画キャンバス（コア体験。これが動かないと話にならない）
2. F8 問題プール（Sheets 連携 / Phase 1.0 は同梱 JSON でも可）

6. F7 リアクション + 図鑑/絵巻
7. F9 設定
8. F1 オープニング（Phase 1.1 で本格化、MVP は仮素材スキップ可）
```

## 5. 開発サイクル制約

- **1 サイクル ≤ 2 時間**（L2 発動閾値の境界。超えるなら設計分割を疑う）
- **ビルド + テスト + lint ≤ 1 分**（CI 基盤要件）
- **コミット粒度: 1 機能単位 or 1 修正単位**

## 6. ファイル配置規則（厳守）


ルート直下の PLAN.md / TODO.md / MEMO.md は禁止。`delivery/` または `docs/` に置く。

## 7. 仕様逸脱時の対応

- 軽微（実装詳細レベル）: L1 が自走判断、DELIVERY.md に記録
- 中程度（機能挙動レベル）: タイプA献上手順（DELIVERY.md に逸脱理由 + 影響範囲明記、L0 確認）
- 重大（SPEC / DONT 抵触）: **即座に L0 spec-architect に差し戻し**、自走しない

## 8. 妹さん配慮の最終チェックリスト（コミット前必読）

- [ ] UI 文言に「学習」「勉強」「テスト」「問題」「正解」「不正解」が無いか
- [ ] 効果音に「ブザー」「失敗音」相当が無いか
- [ ] 配色に「赤＝失敗」演出が無いか（緑は OK、赤は注意マーカー以外避ける）
- [ ] 強制リトライ / スキップ不可の画面が無いか
- [ ] 「次へ」「やめる」「やり直す」が常に画面のどこかにあるか
- [ ] 描画に時間制限が無いか
- [ ] 判定 3 段階（大喜び / 寄り添い / 別角度）以外の表現が無いか
- [ ] フォントが小さすぎないか（最小 16px、推奨 18px）
- [ ] コントラスト比 4.5:1 以上か（WCAG AA）
- [ ] スタイラス / 指描きどちらでも操作できるか

## 9. Council（合議）の起動条件

実装中に下記が発生したら council skill を起動して 3 ペルソナ判断を仰ぐ:

- 複数実装案で confidence < 0.6 の拮抗
- SPEC / DONT に矛盾する実装要請
- 不可逆操作（妹さんのデータ削除を伴う変更等）
- 「妹さんを傷つける可能性がある」設計判断

タイポ修正・フォーマット調整・明確仕様の素直実装では起動しない。

## 10. 献上時の必須項目

L1 献上時、`delivery/DELIVERY.md` に以下を記録:

- 実装した機能 / 動作確認済み項目
- 既知の制約 / 未実装項目
- 仕様逸脱（あれば）
- 推論的センサー結果
- 独立検証で照合してほしい観点（プロジェクト固有）
- 次フェーズ提案
