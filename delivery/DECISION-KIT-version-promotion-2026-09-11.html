私の前回の問いの立て方が不正確だった

「6.19.0 に飛ぶか、6.18.0 を経由するか」と訊いたが、規則を読み直すとこの二択自体が成り立たない。

1. spec 番号は release 番号ではない — 先例が 2 件ある

規則
dev-env-spec.md は「spec 番号 = 起草時の予約 ≠ release 番号」を明文化している。追い越された未実装 spec は番号を付け替えず drafted_as: の追記で扱う。
先例
v6.12.0 の状態行は 「実装済み（PR #191、VERSION 6.15.0）」 — spec 番号と release 番号が違う実例。v6.13.0 F5 は v6.18.0 C-1 として着地（drafted_as の初適用）。
帰結
「6.18.0 を経由する」という経路はそもそも存在しない。上げる番号は spec の並び順ではなく、どの spec の critical が揃ったかで決まる。私の前回の言い方は訂正する。

2. v6.19.0 は昇格条件を充足している

規則
「その版の upgrade-spec の critical 機能がすべて master に入った時点で昇格する。部分実装では上げない」。standard / cosmetic の未実装は昇格を妨げない。
実測
v6.19.0 の priority: critical は F1・F2 の 2 件（#278 / #280）。両方 master。priority: high の F3・F4・F5 も全部 master（#282 / #283 / #284）。critical の未実装は 0 件。
残件
D-3（外部呼び出し元・未特定）と D-4（runtime_profile・未実測）は判断点であって F ではない。規則は critical の実装状況しか見ないため、これらは昇格を妨げない。

3. 昇格を塞いでいるのは v6.18.0 の記述漏れ

実測
upgrade-spec-v6.18.0.md の 7 項目（F0 / C-1 / B-1 / B-3 / C-2 / C-4 / C-3）には priority: の表記が 1 件も無い。v6.19.0 は F1〜F5 の全項目に付いている。
意味
v6.18.0 について「critical がすべて master に入ったか」を機械的にも人間的にも判定できない。唯一未着地の C-3（配布先検査の還流）が critical なのか standard なのかが、どこにも書かれていない。
影響
v6.19.0 だけ上げると v6.18.0 が永久に判定不能なまま追い越される。規則が警戒している「状態行に嘘を書く圧力」がここで生まれる。Q2 がこのキットの実質的な主問。
