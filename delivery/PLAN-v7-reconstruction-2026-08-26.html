dialog-harness — 構造再構築構想

親は、子から
学べない形をしている。

kakuman-platform v3.0 は、DH が持たない機構を 7 つすでに実装している。 routing gate の述語化、規範の分割不変条件、購読量の CI 強制、観測層の非ゲート化、 武装解除センサーの明示 fail、配置と武装の分離、不可逆操作の deny 強制 —— どれも診断書が「DH に欠けている」と指摘したものへの、実運用で証明済みの答えである。 それが親に一つも戻っていない。原因は怠慢ではなく配布トポロジーそのものにある。 本構想は新機構を発明しない。逆流路を敷く。

最も重い一点。check-routing-gates.mjs のコメントは、gate に package.json を含めない理由をこう書く —— 「依存追加のたびに常時発火して gate が形骸化するため」。 頻繁に発火しすぎる検査はゴム印になる という洞察は、DH のどの規範にも書かれていない。 これは運用でしか手に入らない知恵であり、DH は運用を持たないので永久に手に入らない。

構造診断

根因は配布トポロジー

dh-manifest.yml は 4 分類を持つ —— overwrite（丸ごと差し替え）／merge／redeploy／never_touch。 4 つとも DH → プロジェクトの「下り」である。上りの分類が存在しない。 そして DH 本体には SPEC.md も REGIME.md も製品も無い。つまり DH は運用圧を受ける面を一つも持たない。

診断書の 8 所見はすべてこの一形から派生する。DH が「宣言はあるが配線がない」状態を脱せないのは、 配線を要求する圧力が DH に届く構造になっていないから。 kakuman は届いたから作った。DH は届かないから作らなかった。それだけの話であり、思想の問題ではない。

再構築

4 つの構造変更

新機構は発明しない。すべて kakuman に実在する形式を DH の語彙へ移す。移すのは形式だけで、罠 ID や gate 名といった kakuman 固有の内容は持ち込まない（「agent 本体はプロジェクト不変・差異は入力データに閉じる」の逆流への適用）。

A. edge を述語で武装する

GRAPH.yml の edge に predicate を足す。指す先は harness-verifier/predicates/ の関数で、 機械検出できない edge は「書かない」のではなく unmechanizable: true と宣言する。 kakuman の 'G-UX-SNS': []（意味的トリガーゆえ機械検出対象外、段 2 の自己申告へ委譲）の一般化にあたる。

# 現行 — 人間が読む文章しかない
- from: layer1-autonomous-dev
  to: human-P4-停止介入
  type: conditional
  condition: "opt-in 領域に該当（philosophy 改修 / harness-verifier 自己改修 / …）"

# v7 — 読む文章と、評価する述語を分ける
- from: layer1-autonomous-dev
  to: human-P4-停止介入
  type: conditional
  condition: "opt-in 領域に該当（philosophy 改修 / harness-verifier 自己改修 / …）"
  predicate: opt_in_area            # harness-verifier/predicates/opt_in_area.py
  unmechanizable: false
  enforced_by: .github/workflows/auto-merge.yml

B. 除外リストを分割不変条件に置き換える

g5_false_positives を廃止する。代わりに kakuman の check-traps-sync.mjs と同じ不変条件を課す。

C. 観測層を門から切り離す

kakuman の 3 層モデル（床＝required の型・lint・build・test ／ 観測＝非ゲート ／ 門＝停止条件）と罠 X-CI-A / X-CI-B を、DH の規範へ昇格させる。 DH に観測層が無いまま F-03（自動発見）を入れると、発見が wake event を量産して自律実行を食い潰す —— kakuman が 2026-06 に実際に踏んだ道である。順序を逆にしてはいけない。

観測層に課す 4 条

  • required に入れない。観測の失敗で開発を止めない
  • 赤いチェックを作らない。赤＝wake event＝自律実行の消費
  • PR にコメントしない。結果は job summary と artifact にだけ出す
  • 武装解除は黙って緑にしない。secret 不在・設定欠落は明示 fail（rls-drift の規律）

配置と武装の分離

DH に discover.yml を置く。走査対象は 4 種 —— 期限切れの review_trigger ／ 2 cycle 以上続く WARN ／ 滞留 PR・赤い CI ／ 未配線 skill と未解決の申し送り。

schedule: はコメントアウトしたまま出荷する。 武装は人間が行う。消費枠に直結する判断を AI 側に置かない —— これも発明ではなく observe.yml がすでに採っている分担である。

D. 逆流路を manifest に定義する

dh-manifest.yml に第 5 の分類 upstream を新設する。 「プロジェクト側で実装され、DH に還流しうるもの」を宣言し、scripts/upstream-scan.py が配布先と DH master を突き合わせて delivery/UPSTREAM-CANDIDATES-*.md に候補を出す。

upstream:                       # 新設。上りは「候補提示」に閉じる
  scan:
    - ".claude/skills/"          # DH に無い skill / 同名 skill の実質的前進
    - "scripts/"                 # DH に無い決定論センサー
    - ".github/workflows/"       # DH に無い workflow の形式
  never_upstream:                # 逆流を禁じる領域（子が親の憲法を書き換えない）
    - "philosophy.md"
    - "dh-manifest.yml"
    - "auto-merge-boundary.md"
  gate: human                    # 自動 merge しない。候補 md → 人間承認 → DH 実装

continuous-learning（観測 → 候補化 → 人間最終承認）と同じ形である。 あちらは hook 観測ログ起点、こちらは配布先リポジトリ起点。新しい思想は要らない。

移行計画

6 段階

各段は独立に revert 可能で、前段の完了を後段の前提にする。順序には根拠がある —— C（観測層）を D（自動発見の器）より先に置くのは、観測層なき発見が wake event を量産するため。

Phase 0

役割境界の機械化 起草済

v6.13.0（F1 独立検証の隔離実行／F2 opt-in 境界の導出型配線／F3 事後評価の取りこぼし封じ）。 すでに正しい方向を向いている。本構想はこれを置き換えず、F2 の「導出型の配線」を edge 全体へ一般化した続きとして接続する。

Phase 1

逆流路（変更 D）

manifest に upstream ＋ upstream-scan.py。出力は候補 md のみで、DH のファイルを 1 バイトも書き換えない。 最初に置く理由：以降の全 Phase が「kakuman の実装を移す」作業であり、その供給路を先に通しておくのが最も安く、かつ Phase 1 単体でも即座に元が取れる（現在すでに 7 機構 6 skill が待っている）。

完了条件：kakuman v3 に対して scan を回し、候補 md に 7 機構が列挙される。人間が採否を記入できる。

Phase 2

述語層（変更 A）

harness-verifier/predicates/ を新設し、停止条件に関わる edge のみに predicate を付ける （opt-in 領域判定／stop ラベル／H カテゴリ抵触／harness-verify SUCCESS／CTL 閾値／独立検証の隔離）。 この部分集合についてのみ I-2 を反転する。

完了条件：PR #191（opt-in 領域なのに自動マージされた事故）を再現データとして流し、predicate が停止させることを実証する。過去の事故が回帰テストになる。

Phase 3

分割不変条件（変更 B）

g5_false_positives 16 件を unmechanizable 宣言（judged_by ＋ expires_at つき）へ移送し、G-5 を WARN → FAIL 昇格。 未分類 0 件を不変条件にする。

完了条件：16 件それぞれに人間の署名と期限が入り、未分類が 0。以後、経路を足したら分類も足さないと CI が落ちる。

Phase 4

観測層（変更 C）

observe.yml を DH へ移植（非ゲート・非コメント・artifact 出力）。 GRAPH.yml と GitHub API から「いまどの Issue / PR がどのノードに居るか」を出す台帳を job summary に描く。 既存の state の投影であり、新しい state は作らない。

完了条件：観測 job が赤を作らず、PR にコメントせず、台帳が読める。武装解除（token 欠落等）では明示 fail する。

Phase 5

自動発見と authority の実行時化

discover.yml を schedule: 無効で出荷（武装は人間）。 併せて CTL 導出結果を history/ に commit し、issue-pickup / auto-merge が読む。 .claude/settings.json の deny を DH 自身にも置き、L-GATE を機械強制にする。

完了条件：人間が schedule を外した日から、起票提案が自動で立つ。ready-for-ai の付与は人間のまま（philosophy 第 6 条を一切崩さない）。

スコープ外

やらないこと

本構想が明示的に禁じる 6 件

  • philosophy.md を書き換えない。 L-FROZEN-PHIL は 2026-11-06 の評価ゲートまで凍結。本構想は条文が既に要求している内容に実行経路を与えるだけで、条文には触れない
  • 逆流を自動 merge しない。 子で育った規範が親の憲法へ自動流入する経路は、P4 介入権を事後発動化させる。候補提示に閉じ、never_upstream で憲法級を明示除外する
  • kakuman 固有の内容を持ち込まない。 移すのは形式（述語・分割不変条件・非ゲート観測）だけ。罠 ID・gate 名・Supabase 語彙は DH に入れない
  • L3 を新設しない。 観測層も逆流路も既存 4 役割の support 枠に置く（philosophy 第 1 条 §L3 を新設しない）
  • 規範量を増やさない。 追加するのは検査器とスキーマ欄であって条文ではない。f5fc45「減らす・時限化」に反する追加は Phase から外す
  • fan-out と checkpoint を v7 に入れない。 段階 5 / 7 は状態機械の新設を伴う。Phase 1-5 が終わるまで着手しない（一度に根を 2 本触らない）

最大のリスクは Phase 2 にある。 I-2 の部分反転は「宣言が実行を拘束する」への転換であり、宣言を間違えると開発が止まる。 だから対象を停止条件の 6 edge に絞り、過去の事故（PR #191）を回帰テストに使う。 全 edge を一度に述語化しようとした瞬間、この構想は失敗する —— kakuman の gate も 18 本のうち 2 本を「機械検出対象外」と正直に宣言することで生き延びている。

結び

親が子に追いつく

診断書は「憲法と配線図は世界最高水準、電気は通っていない」と書いた。 kakuman v3 を見たあとでは、言い方を変えたほうが正確だ —— 電気は通っている。ただし子の家にだけ通っていて、親の家には配線が来ていない。

これは失敗ではなく、メタハーネスという形態の構造的帰結である。 DH は製品を持たないから本番事故を踏まない。踏まないから機構が要らない。要らないから作られない。 一方 kakuman は 2026-06 に本番 RLS ドリフトを踏み、Actions を課金で止められ、bot コメントで自律実行を食い潰した。 そのたびに機構が 1 つ生まれた。 7 機構はどれも、事故の日付を持っている。

だから v7 でやるべきことは、新しい思想を足すことではない。 親に、子の痛みが届く配線を引くことだ。 upstream という 1 分類、predicate という 1 フィールド、 そして「除外」を「分割」に置き換える 1 つの不変条件。 この 3 つで、診断書の 8 所見のうち 6 つが閉じる。

ハーネスを生み出すハーネスが、ハーネスから学べないままでいるのは筋が通らない。 L0 ループが「対話の蓄積としてハーネスが育つ」ことを核心に据えているなら、 その対話相手は人間だけではないはずだ。稼働している子も、対話相手である。
