Alignment

先に潰しておく認識のズレ

L0 では実装より前にここを合わせる。以下 3 点が未合意のまま進むと、作った後に「思ってたのと違う」が確定する。

Gap 01 — 用語

「Live モードのように」は、2 つの別物を指している

ChatGPT の Live が滑らかなのは speech-to-speech（音声のまま推論）だから。一方、やりたい「タスク実行」は CC / Codex というテキスト前提のエージェントの仕事。この 2 つは別の層に置くしかない。

合意すべき点 — 求めているのは (a) 遅延 1 秒未満の滑らかな会話体験 か、(b) 手を使わずタスクが流れる体験 か。(b) なら案 B で足り、(a) を混ぜると課金構造が変わる。

Gap 02 — コスト構造

「サブスクを起動する」は、音声部分までは含まない

CC / Codex のサブスクが覆うのはテキストの推論まで。音声の入口（STT）と出口（TTS）は別勘定で、ローカル OSS なら 0 円、クラウドなら従量。Realtime API を音声フロントに使う案 C だと、1 日 10 分 × 30 日で概算 $15/月前後が上乗せされる（gpt-realtime-2 系の公称レートからの試算。要実測）。

合意すべき点 — 「追加課金ゼロ」が制約なのか、月 $10〜20 なら許容なのか。ここが案 B / 案 C の分岐点そのもの。

Gap 03 — 権限

「タスクを実行」の射程が決まっていない

読み上げ・要約だけなら安全。だがファイル書き換え・コミット・送信・購入まで含むなら、寝起きの曖昧な発話が不可逆操作に化ける。音声は誤認識する前提で、不可逆操作は必ず音声で確認を返す設計にする（dialog-harness の「人間最終承認」原則と同じ形）。

合意すべき点 — 無確認で実行してよい操作の範囲。初期は「読む・調べる・下書きする」までに閉じるのが安全。

Architecture

ARC 候補 3 案

縦軸は「サブスク枠を守るか / Live 品質を買うか」。中間の案 B が、追加課金ゼロのまま手を使わない体験に届く唯一の位置にある。

案 A — OS 依存

Windows 音声アクセス委譲

OS のアプリ起動コマンドで CC / Codex を開き、以降は OS の音声入力で打鍵を代替する。

利点 実装ほぼゼロ。今日試せる。

欠点 自由発話をエージェントに流す経路がなく、確定操作が毎回要る。Live 感は出ない。

難度 ★☆☆☆☆ / 追加費用 0 円

案 B — 推奨

ローカル常駐 OC

自作の常駐プロセスがウェイクワード・VAD・STT・TTS を束ね、headless の CC / Codex を叩く。

利点 サブスク枠のまま完結。バックエンドを Claude / Codex で差し替え可能。

欠点 往復 3〜6 秒。滑らかさは Live に届かない。

難度 ★★★☆☆ / 追加費用 0 円

案 C — Live 優先

Realtime API を音声フロントに

Realtime モデルが会話を受け持ち、tool call で CC / Codex を呼び出す。

利点 応答 1 秒未満、割り込みも標準で入る。本物の Live 体験。

欠点 音声分が従量課金（概算 $15/月〜）。API キー必須でサブスクの外。

難度 ★★★★☆ / 追加費用 従量

Recommended — 案 B

常駐 OC のパイプライン

音声層（ローカル・0 円）とエージェント層（サブスク枠）を分けて並べたもの。この境界を保つ限り、後から案 C に載せ替えても①〜③と⑤は捨てずに済む。

Latency

発話が終わってから最初の音が返るまでの内訳（GPU 搭載機での概算・要実測）。合計 3.3〜6.4 秒。案 C の Live は同じ区間を 1 秒未満で返す。

Obstacles

壁となるポイント

難度は詰まる確率と回避の効かなさで付けた。上 2 つは設計段階で決着を付けないと、実装が進むほど手戻りが大きくなる種類の壁。

WALL 01

サブスク枠と Live 品質が同じ層に乗らない

難度 高 / 構造的
正体
speech-to-speech は Realtime API の機能であり、CC / Codex のサブスクにその経路が存在しない。実装力では越えられない、契約構造の壁。
兆候
「サブスクのままヌルヌル喋らせたい」という要求が消えないまま実装に入る。
回避
層を割る。音声層を差し替え可能にしておけば、まず案 B で作り、不満が残った時だけ案 C の音声層を被せるという二段構えが取れる。捨てるのは音声層だけで済む。
WALL 02

寝起きの誤認識が不可逆操作に化ける

難度 高 / 安全性
正体
朝一の滑舌・生活音で STT は確実に誤る。音声は「誤認識を前提に設計する入力」であり、そこにファイル書き換えや送信を繋ぐと事故が確定する。
兆候
「なんでも実行できる」を初期スコープに入れてしまう。
回避
操作を 読む / 調べる / 下書きする（無確認可）と 書く / 送る / 消す / 買う（音声で復唱確認）に二分する。復唱確認は遅延を増やすが、ここは削らない。
WALL 03

スピーカー再生音を自分のマイクが拾う

難度 中 / 実装
正体
読み上げ中の自分の声でウェイクワードが再発火し、無限ループや会話崩壊を起こす。バージインを入れると必ず踏む。
兆候
スピーカー運用で「勝手に喋り続ける」「自分の返事に反応する」。
回避
初期はヘッドセット前提で逃げる（実質ゼロコスト）。スピーカー運用を要件に入れるなら AEC（エコーキャンセル）が必要で、難度が一段上がる。
WALL 04

スリープした PC は声で起こせない

難度 中 / OS 制約
正体
スリープ中はマイク入力が止まる。スマートスピーカーのような常時待機は、専用ハードだから成立している。
兆候
「朝いちばんに声をかけたのに無反応」。
回避
タスクスケジューラで定刻に PC を自動起床させ、OC を先に立ち上げておく。声は「起こす合図」ではなく「待っている相手への呼びかけ」に意味を変える。要求の本質は満たせる。
WALL 05

非力な PC では STT が間に合わない

難度 中 / 実機依存
正体
GPU なしの 7〜8 万円クラスだと faster-whisper の中〜大モデルは実用速度に乗らない。要求仕様ではなくマシンが上限を決める唯一の箇所。
兆候
喋り終わってから文字になるまで数秒かかり、会話のリズムが壊れる。
回避
着手前に実機で tiny / base / small を並べてベンチを取る（Phase 0）。落ちない場合はSTT だけクラウドに出す（月数百円規模）。この分岐は早く決めるほど安い。
WALL 06

常駐プロセスの寿命とトークン失効

難度 低 / 運用
正体
OAuth トークンの失効、CLI の更新、PC 再起動で、ある朝いきなり黙る。自動化の常。
兆候
「昨日まで動いていたのに反応しない」。
回避
OC の起動時にバックエンドへ ping を打ち、失敗したらその場で声で伝える（黙って死なせない）。ログを 1 ファイルに寄せておけば復旧は数分。

Open Questions

返答が要る未決事項

Q1

優先するのは「滑らかさ」か「手を使わないこと」か

前者なら案 C（従量課金）、後者なら案 B（0 円）。Gap 01 の合意点。

→ 滑らかさ優先 / 手を使わない優先 / まず 0 円で試して判断
Q2

音声部分の追加課金はどこまで許容するか

「サブスク以外は 1 円も払わない」が制約なら、案 C と STT のクラウド化が同時に消える。

→ 追加課金ゼロ厳守 / 月 1,000 円まで / 体験が良ければ月 2,000〜3,000 円可
Q3

朝いちばんに実行したいタスクの具体例は

3 つ挙がれば、それが受け入れ基準になる。「予定の読み上げ」と「リポジトリの差分確認」では必要な権限が違う。

→ 例：予定確認 / 未読要約 / 昨日の作業の続き / 今日やることの整理
Q4

マイクはヘッドセットか、スピーカー運用か

ヘッドセットなら WALL 03 が消えて難度が一段下がる。スピーカー運用は要件に入れると跳ね上がる。

→ ヘッドセットで可 / 手ぶらで話したい（AEC 必須）
