## 1. 「静かな失敗」の定義

**定義**: 機構が本来の働きをしていないのに、その不作動が誰にも観測されず、
苦情・エラー・赤い CI のいずれも生まないまま持続する状態。

対義は「痛む失敗」— 落ちる・止まる・怒られる。DH の既存検出スタックはほぼ全てこちらを見ている。

### 静かな失敗の 3 つの必要条件

| 条件 | 内容 | 破れば静かでなくなる |
|---|---|---|
| **C-1 不作動が出力を持たない** | 動かないことが成果物の欠如としてしか現れない | 動かないと例外を投げる設計にする |
| **C-2 期待する主体がいない** | 「これは動いているはずだ」と誰も確認しない | 定期的に問う主体を置く |
| **C-3 代替経路が肩代わりする** | 本来の機構が死んでも別の何かが仕事を吸収し、表面上は回る | 代替経路を可視化する |

**C-3 が最も厄介である**。代替経路があるからこそ誰も困らず、困らないから直らない。

## 4. 3 つの静かな失敗の型と、それぞれの検知可能性

実例から 3 つの型が抽出できる。**型ごとに難度がまったく違う**ことが重要である。

### 型 A: 宣言と実体の乖離（v6.17.0 が塞いだ型）

「在るのに宣言されない」「宣言したのに無い」。
**決定論で検知できる。** 両側を数えて突き合わせればよい。v6.17.0 の 13 検査がこれ。

### 型 B: 時間で腐るものの停止（F7 / F8 が塞いだ型）

「動いていたものが動かなくなった」。
**決定論で検知できる。** 最終実行時刻と現在時刻の差を数えればよい。
ただし**閾値の設定が本質的に恣意的**で、`I-4`（常時発火する検知を作らない）との緊張が常にある。

### 型 C: 配線されているが通電していない（**未着手**）

「経路は存在し、宣言も実体も正しいが、実際には一度も通っていない」。
kakuman の hook 7 件、読まれない RL 6 本、使われない正典手順がこれ。

**これは決定論では検知できない。** なぜなら「通ったこと」の記録がそもそも残らないからである。
検知するには**実行の痕跡を残す仕組みを先に作る**必要があり、それは新しい常駐機構になる
（`telemetry-reflux.rules.md:22-23` TR-4 / `ritual-protocol.md:148-164`「新しい常駐機構は作らず
既存の儀式に寄生する」と正面から衝突する）。

## 5. 型 C にどう向き合うか — 3 つの案と評価

### 案 1: 実行痕跡を残す（棄却）

全 skill / RL / 手順に「読まれた」「実行された」の記録を残させる。
**棄却理由**: 新しい常駐機構であり TR-4 に反する。かつ痕跡の記録自体が動かなくなれば同じ問題が再発する
（メタレベルの静かな失敗）。観測のための機構が観測されない、という無限後退。

### 案 2: 定期的に「これは動いているか」を問う主体を置く（有望）

C-2（期待する主体がいない）を破る。**新しい機構ではなく既存の儀式に寄生させる**。

L0 振り返り儀式 F1 は既に `council-log-sync.py` と `council-axis-audit.py` を走らせている
（`ritual-protocol.md:88-95`）。ここに「**今 cycle で一度も使われなかった配布物**」を
列挙するステップを足す。判定はせず、数えて人間に見せるだけ（I-2）。

**利点**: 痕跡の記録を必要としない。「使ったものを申告する」のではなく
「**使わなかったものを問う**」向きにすれば、儀式の中で人間が答えられる。

**限界**: 人間の記憶に依存する。cycle をまたいだ長期の不作動は見落とす。

### 案 3: 「点検」を制度化する（最有望・実績あり）

**8 項目すべてを発見したのは点検である。** これは偶然ではない。
点検は「痛みを待たずに外から走査する」という、静かな失敗に対する唯一の実績ある手段だった。

v6.17.0 の起点になった点検は `delivery/ANALYSIS-code-knowledge-graph-2026-09-05.md` に記録された
Workflow `wf_1842b5a4-d85`（29 エージェント / 所見 113 件 / 反証 12 件）である。
**これを不定期の英雄的行為ではなく、規定のリズムを持つ儀式にする。**

**利点**: 実績がある。新しい常駐機構を作らない（点検は都度起動）。LLM を使うが、
これは検知ではなく**探索**であり I-3（検知は決定論）の射程外。

**要検討**:
- リズムをどう定めるか（cycle 数 / 期間 / 版の区切り）
- 点検の対象範囲をどう決めるか（毎回全域は高コスト）
- 点検自体が静かに行われなくなる可能性（メタ問題は残る — ただし
  `signal-scan` の検知器 (c) `review_trigger` が「規範ファイルが N 日更新されない」を既に見ており、
  点検の記録ファイルをその対象に含めれば部分的に拾える）

## 6. 提案 — 最小の第一歩

**案 3 を骨格に、案 2 を補助とする。** ただし本分析では**実装しない**。以下は次サイクルへの提案である。

### 提案 1: 点検にリズムを与える（型 C の主対策）

- `dev-env-spec.md` に「点検」を儀式として定義する。契機は**版の区切り**（minor 昇格時）
- 点検の記録は `delivery/ANALYSIS-*` に残す（既存慣行）
- `signal-scan` の検知器 (c) `review_trigger` の対象に点検記録を含め、
  **点検が行われなくなったこと自体を型 B の検知で拾う**（メタ問題の部分的解決）

### 提案 2: 儀式で「使われなかったもの」を問う（型 C の補助）

- `ritual-protocol.md` の F1 に 1 ステップ追加。「今 cycle で一度も参照しなかった配布物はあるか」
- 判定せず列挙のみ（I-2）。答えは人間が持つ

### 提案 3: 静かな失敗を分類語彙として登録する

- `glossary.yml` に「静かな失敗」を定義語として追加し、型 A / B / C を区別できるようにする
- 以後の spec が「この欠落はどの型か」を問えるようになる。**型 C と分かった時点で
  決定論検知を諦め、点検か儀式に回す**という判断が機械的にできる

### 提案しないもの

| 除外 | 理由 |
|---|---|
| 実行痕跡の記録機構 | TR-4 違反（新しい常駐機構）+ メタレベルの静かな失敗を生む（§5 案 1） |
| 型 C の決定論検知 | 原理的に不可能。痕跡が無いものを数えることはできない |
| 点検の自動化 | 点検は探索であり LLM を要する。自動化すると I-3 の境界が曖昧になる。**起動は人間または儀式** |
