Council の二つの実行方式

同じ Council 規範に、サブエージェント手動フローと Workflow という二つの実行基盤がある。v6.11.0 は後者を既定、前者を degrade 経路と定めた。両者は「何を出すか」ではなく「規約で守るか、構造で守るか」で分かれる。

まず結論

  1. 判定の中身は変わらない。重み・帯・ペルソナ人格・final_decision: null・H カテゴリ人間専管はどちらも同一の正典に従う（不変条件 I-1）。差が出るのは規律の担保方法だけ。
  2. Workflow は規約を構造に置き換える。情報純度・schema・重み計算・ログ書式が「守る約束」から「破れない配線」になる。代償は逐次可視性・人間の割り込み・モデルティアの手動制御。
  3. ただし「Workflow 化 = 決定論」ではない。同じ v6.11.0 でも council-fanout は決定論 JS、review-pipeline は重み計算まで LLM に投げている。差は基盤ではなくスクリプトの書き方に宿る。

01 / 骨格制御フローを誰が持っているか

これが唯一の本質的な差で、以下すべてはここから派生する。

A — subagent 手動フロー

モデルが手順書を読んで進める

本体セッション（CI では OC = Opus）が SKILL.md §処理フローを読み、Task ツールで leaf subagent を起動する。順序・並列性・入力の切り分けは、その場のモデルの読解に依存する。

subagent は subagent を生成できない（委譲は 1 階層）。中間結果はすべて呼び出し側のコンテキストに戻る。

.claude/skills/crosscut-council/SKILL.md
.claude/agents/review-persona-*.md
B — Workflow

スクリプトが制御フローを保持する

council-fanout.workflow.mjs が Phase 0 → 重み → Phase 1 → 対立度 → Phase 3 → ログ生成を JS として持ち、LLM が要る箇所だけ agent() に委譲する。順序も並列性も入力の切り分けもコードが決める。

メインコンテキストに戻るのは最終結果と log_block だけ。Date.now() / Math.random() は禁止（再開キャッシュを壊すため）で、invocation_id と timestamp は呼び出し側が採番して args で渡す。

05 / 落とし穴Workflow 化しても決定論とは限らない

同じ v6.11.0 で書かれた 2 本のスクリプトの間に、無視できない落差がある。ここを「Workflow だから安全」と読むと、規律は移らない。

council-fanout（F1）

決定論を最大化した実装

フィールド単位の schema、JS でのスコアリングと帯計算、ログ書式の生成まで機械が持つ。LLM が触るのは persona の観測と judgment の言語化だけ。

review-pipeline（F2）

構造化だけを強制した実装

schema は { type: 'object' } のみ（既知の限界 L-1）。final_weights の計算も weighted_score の適用も agent 任せで、難度 tier は計算するが分岐に使わない（L-4）ため常時フル合議になる。

したがって差異の主語は「基盤」ではなく「どこまでを JS に降ろしたか」である。Workflow は決定論を可能にする器であって、決定論そのものではない。

06 / 不変どちらでも変わらないもの

  • 実行基盤は判定を持たない（I-1 / escalation-matrix）。final_decision は常に null、決めるのは人間か合意プロセス。
  • H1–H4 は人間専管。Workflow に渡しても即 escalate_to_human で返る。
  • degrade は機能停止ではない（仕様 C-2）。Workflow tool 非対応環境・judgment_failed 時は手動フローで完遂し、人間に warn を残す。つまり手動フローは旧式ではなく、現役の縮退経路である。
  • journal は reviewer に渡さない（I-4）。実行側の内部成果物であり、独立検証のコンテキスト隔離を破らせない。
  • 並列度の既定上限（F7-2）: Council fan-out 3+1 / review ≤ 8 / 反証 = critical 機能 × 3 / 協調層 teammate ≤ 3。超過は ADR 必須。
  • 第 3 階層（議論型協調層 / Agent Teams）は未導入。規範が定義するのは抽象契約のみで、実装固有情報は時限メタデータ付きで templates/experimental/ に隔離される（F6）。

07 / 適用DH 更新への持ち込み候補

以下は判断材料であって決定ではない。採否は人間が決める（philosophy 第 6 条）。

P1

既定が使われていない事実を先に片づける

「Workflow が既定」と規範が言う一方、直近 3 発動は手動書式で記録されている。規範と実運用の乖離は v6.1.0 の CTL 分断と同型の空文化。degrade を選んだなら理由を、選んでいないなら起動導線を直す。

P2

実行方式をログに明示フィールドで持つ

いまは confidence_band の有無という副作用から推定している。execution_mode: workflow | manual の 1 フィールドがあれば、degrade 率が CTL と同じ精度で観測できる。

P3

review-pipeline の落差を閉じる

L-1（フィールド schema）と L-4（難度ゲート未配線）は v6.11.0 が自ら次サイクル送りと記録した宿題。閉じるまでは CI 側の tier1 軽量分岐を残す前提が続く。

P4

失われた側——人間の割り込み——を補う

手動フローの実利は逐次可視性と途中介入だった。Workflow ではそれが無い。notes フィールド（仕様 C-3）は枠外の異見を拾う弁だが、走行中に人が向き直す手段の代替ではない。何を代替に置くかは未定義のまま。
