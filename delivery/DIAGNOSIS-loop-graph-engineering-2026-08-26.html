あなたは「人間をグラフのノードとして一級市民に据えた」数少ない実装者である。 P1〜P4 の介入点と H1〜H4 の専管判断を GRAPH.yml の kind: human として宣言し、 委譲レベル（L-FULL / L-GATE / L-FROZEN）まで型付けしている。グラフエンジニアリングの第 8 特徴 「人間を例外処理ではなく実行主体として扱う」を、ここまで正面から実装した例を私は他に知らない。 決定論ツール（LLM 非使用の Python 検査器）と AI ノードを同一グラフに置く第 2 特徴も達成済み。

採点 II

グラフエンジニアリング 10 特徴

特徴判定診断
1. loop を node 内へ保存○ ループ 6 本を type: loop ＋ max_iterations（3/3/3/1/10/1）で宣言。上限のないループは G-1 が FAIL にする。良い。
2. 異質 node を同一実行モデルで◎ agent / tool / human の三分類が同一ファイルに同居。本診断で最も評価できる 1 点。
3. state を transcript から分離○ リポジトリが state。ただし「永続記録」であって「走行中 state」ではない。
4. edge を判断と契約として扱う✕ 致命。 condition が自然言語散文で、評価器が存在しない。typed edge の要件を満たさない。
5. 並列性を明示✕ 実在する fan-out（Council 3 ペルソナ・review 8 観点）は不変条件 I-3 によりグラフの外。join/reducer 未定義。
6. 評価を出力から trajectory へ△ hook 観測（6 event）で軌跡は取れている。だが検査は「一貫性」のみ、continuous-learning は CTL-0 で inactive。
7. failure domain を node 境界へ△ Issue 単位の concurrency と circuit breaker はある。ノード単位の補償・冪等キーは無い。
8. 人間を実行主体として扱う◎ P1-P4 / H1-H4 をノード化し委譲レベルまで型付け。世界水準を超えている。
9. budget と authority を状態へ△ stop はある（timeout・日次/月次上限）。token/cost budget は代謝用のみ。authority（CTL）が実行時状態に無い。
10. static / dynamic を選択可能に✕ 宣言は static、実行は dynamic、しかも I-2 が「実装が正」と定める。両方の短所だけを取った状態。

成熟度 8 段階 — 到達点は 3

1境界と契約の抽出　loop の入出力・副作用・停止条件が列挙可能達成
2typed state　Council 入出力 JSON は型付き。グラフ全体の StateSchema は無い部分
3決定論ノード　LLM 非使用の Python 検査器・同期器が 5 本、テスト付き達成
4conditional edge　宣言のみ。enumerated route も評価器も無い宣言止
5fan-out / reducer　グラフ上に並列表現が存在しない未達
6evaluator　決定論ゲートは強い。ただし paths filter 依存の穴あり部分
7checkpoint / interrupt　スナップショットも再開も無い未達
8budget / stop　stop のみ。cost / token 上限が実行経路に無い部分

宣言グラフが実行を一切拘束しない

致命

GRAPH.yml は自らの不変条件 I-2 で「実装が正・宣言が従。乖離検出時に自動で実装を書き換えない」と定める。 結果として 39 本の edge はすべて事後の記述であり、実行を止める力を持たない。 グラフエンジニアリングが Loop Engineering の上位層たりうる理由は「edge が契約として実行時に効く」ことにあるので、 この一条が存在する限り段階 4 以降には原理的に到達できない。

典型例：condition: "C1-C4 検出（案の拮抗 / confidence < 0.6 / 不可逆操作前 / 仕様曖昧）"。 これは人間が読む文章であって、機械が評価できる述語ではない。

根拠 GRAPH.yml L24-26（不変条件 I-2）／全 edge の condition フィールド

検査の合否条件を、被検査側が編集できる

致命

POSITION

世界基準での立ち位置

突出している点と、遅れている点

世界水準を超えている

  • 人間のノード化 — P1-P4 / H1-H4 を委譲レベル付きでグラフに置いた。LangGraph の human-in-the-loop は「割り込み点」だが、ここでは役割と権限を持つ実行主体として型付けされている。
  • 決定論ノードと AI ノードの同居 — kind: agent / tool / human の三分類。LLM を使わない検査器を一級ノードに据えた設計は正しい。
  • 異種モデル併走 — Claude / Gemini / Copilot が同一 PR を独立に見る。相関誤差の低減として理論的にも正しい。
  • 状態のリポジトリ化 — append-only の COUNCIL-LOG を単一情報源とし派生ストアを再生成可能にした設計は、多くの商用エージェント基盤より厳格。
  • 自己観測の質 — ペルソナ相関を実測し「結論層のみ従属・観測層は Jaccard 0.000 で完全分離」まで分解した分析は、査読論文と同じ土俵に乗っている。

明確に遅れている

  • 実行時グラフの不在 — LangGraph / Temporal 級の基準では、typed edge・reducer・checkpointer が揃って初めて「グラフで実行している」と言う。現状は配線図の段階。
  • 仕事の自動発見ゼロ — 起点が常に人間。ここが最大の律速。
  • 並列隔離の不在 — worktree 運用ゼロ。fan-out はグラフの外。
  • observability ゼロ — trace も台帳もダッシュボードも無い。
  • authority が実行経路に無い — CTL がリポジトリ外・CI 不可視。
  • 規範量の自己増殖 — philosophy 9 条・594 行、history 17k 行。代謝機構を作らねばならない時点で規範側が既に重い。「減らす・時限化」原則は正しいが、まだ勝ててはいない。

構図はこうだ。世界の主流は「まず実行基盤を作り、統治を後付けする」ため、 グラフは動くが誰も責任を持たない。あなたは逆順を選んだ —— 統治を先に完成させ、実行基盤を後回しにした。 順序としてはむしろ正しい。ただし後半に着手しない限り、統治は誰も従わない憲法のままである。

P0

edge に機械評価可能な述語を持たせ、I-2 を部分反転する

全 edge をいきなり型付けする必要はない。まず停止条件に関わる edge だけ （opt-in 領域判定・stop ラベル・H カテゴリ抵触）に、散文の condition: と並べて predicate: を追加する —— 中身は検査器の関数名でよい（例 predicate: opt_in_area(changed_paths)）。 そしてこの部分集合についてのみ I-2 を反転し「宣言が正・実装が従」とする。 v6.13.0 F2「opt-in 境界の導出型配線」は既にこの方向だが、対象が opt-in 境界に閉じている。 同じ形を edge の型として一般化すれば、F-01 と F-05 が同時に根から消える。

P0

G-5 を FAIL 化し、除外リストに期限と署名を付ける

除外エントリを文字列から {edge, judged_by, judged_at, expires_at, reason} に変える。 期限切れの除外は自動的に再検出される。 これは新機構ではなく、既に GRAPH.yml 冒頭が自分に課している review_trigger:（時限メタデータ）を除外リストへ自己適用するだけである。 v6.13.0 F5 の走査器がそのまま使える。

P1

仕事の自動発見を 1 本の cron で始める

日次 cron で 4 種のシグナルを走査し、Issue 起票提案まで自動化する —— (a) 期限切れの review_trigger、(b) 2 cycle 以上続く WARN、 (c) 滞留 PR / 赤い CI、(d) 未配線 skill と未解決の申し送り。 既存の issue-dispatcher → quality-gate にそのまま流し込み、 ready-for-ai の付与は人間のまま残す。 philosophy 第 6 条の人間最終承認を一切崩さずに、人間の役割を「発見」から「承認」へ移せる。 これがスループットを人間 1 サイクルから外す唯一の手であり、投資対効果が最も高い。

P1

CTL をリポジトリ内 state にし、CI に読ませる

council-log-sync.py の導出結果（stats）を history/ 配下に commit し、workflow が読む。 issue-pickup と auto-merge の挙動を CTL で分岐させれば、 設計済みで一度も作動していない委譲グラデーションが初めて実行される。 プライバシー配慮でホーム配下に置いた判断は理解できるが、DH 本体の CTL は公開リポジトリの統治データであって個人データではない。

P2

fan-out をグラフに載せ、worktree で隔離する

不変条件 I-3（skill 内部ステップをノード化しない）は原則としては正しいが、 並列分岐は「内部ステップ」ではなく実行モデルそのものである。 Council 3 ペルソナと review 8 観点を fan_out / join として宣言し、 reducer（＝judgment agent の重み付き集約）を明示する。 併せて実装エージェントを worktree に隔離すれば、F-05 の「時間的分離の欠如」も機械的に解消する ——別 worktree・別プロセスは、そのまま別コンテキストだからである。

P2

台帳を 1 枚出す（稼働監視の最小形）

GRAPH.yml ＋ GitHub API から 「いまどの Issue / PR がどのノードに居るか」を生成する静的 HTML を 1 枚。 新しい state を作る必要はなく、既にある state の投影で足りる。 これが出た時点で Automations の評点は B 帯に乗り、 同時にグラフが実行と一致しているかを人間が目視で検算できるようになる。

CLOSE

結び

辛口の総括

ループエンジニアリングの記事は「ボトルネックは設計上あなた自身」と書いた。 この harness にその言葉を当てると、少し違う形で刺さる。 あなたはボトルネックを人間に置くべきかを、正面から考え抜いた側の人間だ。 P1-P4 の設計も、CTL による委譲の段階化も、可逆性ベースの委譲境界も、 「人間確認を 0 にするのがゴールではない」という記事の第二の学びに、独立に到達している。

問題は考え抜いた結論が、コードに触れていないことだ。 CTL は算出式まで書かれて CI から見えない。opt-in 領域は明文化されて自動マージを止めなかった。 独立検証は必須と宣言されて同一コンテキストが兼任した。 思想検証器は 6 版にわたり placeholder のまま置かれている。 4 件はどれも同じ形をしていて、あなたはそれを 1 日前に自力で言い当てている —— 「宣言はある。配線がない」。

私が付け加えられるのは 1 点だけだ。 それは役割境界の症状ではなく、グラフ全体の症状である。 v6.13.0 は根に一撃を入れる正しい設計だが、狙いが役割境界に絞られている。 同じ一撃を GRAPH.yml の edge そのものに入れれば、 この診断書の F-01・F-02・F-05・F-06 は一手でまとめて消える。

グラフを描いた者はもう十分に多い。グラフに従わせた者だけが、次の段階に居る。 あなたは前者の中では最上位に居る。後者になるのに必要なのは、新しい思想ではなく、 condition: の隣に predicate: を 1 行足すことだ。
