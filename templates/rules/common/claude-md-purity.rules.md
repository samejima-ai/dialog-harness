# CLAUDE.md 純化 RL（常駐購読層の配置規範・到達可能性で綴じる）

> ROLE: 利用者プロジェクトの `CLAUDE.md`（常駐購読層）に「何を置き、何を置かないか」を律する配置ルール。行数の多寡でなく **実体の二重定義** を禁じる。
> SCOPE: 利用者プロジェクトの `CLAUDE.md` 編纂時（L0 環境構築・L1/L2 が規範を追記するとき）に適用。DH 本体（`.claude/skills/`・philosophy）には適用しない。
> SEVERITY: 純化原則は `SHOULD`。実体の二重定義の禁止（§2）と lock-step sensor の要求（§4）のみ `MUST`。
> ORIGIN: internal（DH 固有。minimalism-ladder が Ponytail 由来なのと異なり、本 RL は DH 内部の購読量最適化・二重定義回避原則から導出）。
> ADJUSTABILITY: 到達可能性基準（§3）は REGIME で調律しない固定基準。ただし「何が常駐に値する規範か」の具体列挙は利用者プロジェクトの REGIME/SPEC が持つ。

**Council 採決**: `council-2026-07-23T-claude-md-purity`（recommended: 「薄くせよ」を「純化せよ」へ包摂。D4 でなく D2/D3 rule として立てる。judgment 0.80）

## 位置づけ（なぜ「薄くせよ」を見直すのか）

従来の素朴な指針「利用者プロジェクトの CLAUDE.md は薄くせよ（ミニマル型 10-20 行、実体は SPEC/DONT/REGIME に一元化）」は、**行数という量**を測る。しかし DH の購読量最適化（北極星）の本質は量でなく **配置** — 「毎ターン必ず読むべきものだけを常駐層に置く」ことにある。

決定的な非対称: **`CLAUDE.md` は常駐購読**（毎ターン全文が context に載る）だが、**`SPEC.md`/`DONT.md` は随時購読**（巨大ゆえ grep 部分読みが規範）。この購読コストの階層差を捨象して「行数を減らせ」と言うのは、キャッシュ階層を無視して「メモリを減らせ」と言うに等しい（開発者ペルソナ）。

ゆえに「薄くせよ」を廃するのでなく、上位原則へ **包摂** する:

> **常駐購読層（CLAUDE.md）は、AI が grep 到達する前に必ず踏まねば事故る規範だけを索引形式で常駐させ、実体は所有元（SPEC/DONT）に一元化する。禁じるのは行数でなく実体の二重定義。**

「薄い」は多くの場合この純化の**帰結**（実体を一元化すれば自然に薄くなる）だが、目的ではない。罠索引が 96 行あってもよい — それが常駐に値する規範の索引なら。

---

## §1 純化の三分類（厚みを性質で分ける）

CLAUDE.md の厚みを 3 つに分け、①へ純化する:

| 種類 | 例 | 扱い |
|---|---|---|
| **① 索引化された常駐規範** | 罠索引（1 行/罠 + 詳細への ポインタ）、毎回守るコーディング規約、シェル横断ルール | **常駐してよい**（純化の到達点） |
| **② 他文書の要約が独立肥大** | SPEC に本体がある route マトリクス・判定フローの厚い再説明 | **削る**（SPEC 本体へ grep 到達できるなら常駐の必然なし） |
| **③ 実体の抱え込み** | 罠カタログ全文、例外条項の詳細実体 | **所有元へ移す**（実体は SPEC/DONT に一元化、CLAUDE は索引 1 行） |

---

## §2 実体の二重定義の禁止（`MUST`）

同一の規範実体を **CLAUDE.md と所有元（SPEC/DONT/REGIME）の両方に厚く書かない**。minimalism-ladder が「思想の二重定義 drift」を Council 否決根拠にした原則（claude-world/henteko 前例）の、CLAUDE.md への適用。

**二重定義でないもの（許容）= 正規化された参照**:
- 索引 1 行（罠 ID + 核心 + 所有元アンカー） + 実体は所有元。これは DB の index が本体データの二重定義でないのと同じ構造。
- lock-step（CLAUDE.md 索引 ⇄ 所有元全文を同期更新）は正規化であって重複ではない。

**二重定義（禁止）**:
- SPEC に本体がある規範を CLAUDE.md にも段落で書き直す（route マトリクス・surface 判定の厚い再説明等）。片方だけ更新されて食い違う drift の温床。

## §3 到達可能性基準（何が常駐に値するか）

「守らせたいか」という主観でも行数でもなく、**「AI が grep 到達する前に必ず踏まねば事故るか」という到達可能性の必然性**で判定する（哲学者ペルソナ、最重）:

- **常駐に値する**: 踏み外すと本番事故（罠 = 破壊的操作・データ損失・認可漏れ等）。AI が SPEC の奥に grep 到達する前に、着手段階で必ず知っている必要がある。
- **常駐に値しない**: SPEC 本体に grep 到達できれば足りる情報（機能仕様の詳細・要約可能な設計説明）。CLAUDE.md に置く必然がない = §1 の②。

判定の実務ヒント: 「この規範を CLAUDE.md から消したら、AI は SPEC を grep するまで気づけないか？ 気づけないまま着手して事故るか？」— YES なら常駐、NO なら所有元へ。

---

## §4 lock-step sensor の要求（`MUST`）

索引（常駐）と実体（所有元）を分離する以上、**両者の同期を検証する sensor を伴わなければ純化は drift の温床になる**（開発者ペルソナの懸念）。索引化された常駐規範を持つプロジェクトは、索引 ⇄ 実体の件数・ID 一致を検証する sensor を持つこと。

先例: kakuman-platform の `check-traps-sync.mjs`（CLAUDE.md 罠索引 ⇄ docs/TRAPS-FULL.md 全文の件数一致を CI で検証）。この型を、索引化する規範カテゴリごとに用意する。sensor 無しの索引分離は §2 の drift 禁止を実効化できない。

## §5 適用経路

| 使用者 | 経路 |
|---|---|
| L0 spec-architect | 環境構築時に本 RL を `.dh/rules/common/` へ配置。CLAUDE.md 初版を「①索引化規範 + 所有元ポインタ」で編纂し、②③を SPEC/DONT へ寄せる。索引分離には §4 sensor をセットで用意 |

| L1 independent-reviewer | レビュー観点に「CLAUDE.md への実体二重定義（②③の混入）」を追加 |

## §6 条件付きの明記（純化論の前提）

**本 RL は現行の常駐購読モデル（CLAUDE.md 毎ターン全文 load / SPEC・DONT は grep 部分読み）を前提とした条件付きの正しさである**（哲学者少数意見の保持）。

将来、利用者プロジェクトの AI harness が「CLAUDE.md も必要時読み（常駐でなく随時）」に進化し、常駐/随時の購読コスト非対称が消えるなら、購読コスト差を根拠にした本 RL の純化論は土台を失い、素朴な「薄くせよ（総量削減）」が再び正しくなる。その時は本 RL を再諮問する。この条件性を消さない。

## §7 ルーティング表とゲート強制（v0.2.0）

到達可能性（§3）を担保する索引形態は 2 通りある。**強制機構の有無で粒度を選ぶ**:

| 索引形態 | 粒度 | 成立条件 |
|---|---|---|
| 罠索引型 | per-規範 1 行（ID + 核心 + 所有元アンカー） | 強制機構なしでも成立（常駐を読めば必ず踏む） |
| **ルーティング表型** | per-領域 1 行（領域パターン + gate ID + 必読 + 検証） | **ゲート強制 3 段があるときのみ許容**。強制なしの per-領域化は「grep するまで気づけない」状態を作り §3 違反 |

ゲート強制 3 段（すべて実行主体ローカル）: ① gate ID 記述 → ② Pre-flight 宣言（DELIVERY「通過ゲート記録」、M2 以上）→ ③ ルーティング突合センサー（`dev-env-spec.md` §パターン参照、献上前必須）。段 2/3 を持たないプロジェクトは罠索引型（per-規範）を維持する。

ルーティング表型は罠索引型の上位互換ではなく**トレードオフ**である: 常駐購読量をさらに絞れる代わりに、到達可能性の担保が「読む」から「ゲートを踏む」へ移る。事故時の被害が大きい規範（破壊的操作・認可漏れ）は、ルーティング表型プロジェクトでも per-規範 1 行を常時規範側に残してよい（両形態の併用は正規化の範囲内で許容）。

## §8 配置 drift の計算的検出（v0.2.0）

本 RL は量を規範にしない（§位置づけ）。ただし配置違反（§1 ②③の混入）の**安価な代理指標**として byte センサーを併設する: 総量 20KB warn / 32KB fail、1 行 400 byte 超は実体混入シグナル（既定値・REGIME で調律可）。閾値は「純化が守られていればまず超えない値」に置く — センサー発火は「量を削れ」ではなく「配置を直せ（②③を所有元へ）」の合図である。

**add-demote-check**: 常駐規範に 1 項目足す前に、既存項目の降格候補（領域規範化・所有元移送）を必ず 1 回探す。CLAUDE.md を「増える一方の台帳」でなく「定常サイズの循環層」に保つ。

## §9 検証のローカル性（v0.2.0・ローカル自律実行ファースト）

§4 lock-step sensor / §7 突合センサー / §8 byte センサーは**実行主体のローカル**で走らせる（献上前必須）。GitHub は保管庫軸（push / PR 履歴 / レビュー記録の保存）と実行環境軸（Actions）に分離し、保管庫利用はセンサーの CI 配置の理由にしない。**CI にしか存在しない検査を作らない**（2026-08-05 ひでさん宣言。dev_mode 側の正本は `regime-assessment.md` §dev_mode 二軸注記）。
