# 最小主義ラダー RL（実装工芸・可逆性で綴じる）

> ROLE: 実装時に「書かないコード」を優先し、要求されない複雑性の増殖を止める言語横断ルール。
> SCOPE: L1/L2 の**実装フェーズ**に適用（対話段階 L0・検証センサーには適用しない）。目的非依存。
> SEVERITY: ラダーは `SHOULD`（既定）。逸脱は要正当化だが欠陥ではない。第 7 段の品質ゲートのみ `MUST`。
> ORIGIN: external（[Ponytail](https://github.com/DietrichGebert/ponytail) v4.x, MIT License, DietrichGebert 氏 / 「最良のコードは書かないコード」の決定ラダーを観測）。原典の散文・常時 active 注入・Ultra「要件異議」モードは**取り込まず**、コードレベルのラダーのみを DH 固有の尺度（可逆性）で再構成した。観測事例としての位置づけは DH 側 `.claude/skills/layer0-spec-architect/references/observed-peers.md` を参照。
> ADJUSTABILITY: 本 RL は REGIME で締緩を調律できる（後述 §締緩の調律）。探索・prototype ドメインでは緩める。

**Council 採決**: `council-2026-07-05T10:37:44Z-pony01`（recommended B: D2/D3 scaffold rule 化。哲学者の第 3 の道を織り込んだ止揚案 B′ で確定）

## 位置づけ（なぜ DH に要るか）

DH の philosophy（9 条）は統治・責務・可逆性・合議に重心があり、「実装時にコードを少なく書く」という**実装工芸レベルの規範はほぼ空白**だった。本 RL はその空白を、DH 本体（D4 = philosophy）を触らずに **D2/D3（利用者プロジェクトへ L0 が配布する scaffold rule）** として埋める。

DH 固有の綴じ直し（Ponytail 原典との差分）:

- 原典は「量（何行減らせるか）」を規範化する。DH は**可逆性を尺度**とする。**書かないコードは最も可逆**（消す対象すら存在しない）ため、最小主義は philosophy 第 9 条「委譲境界原則（可逆性ベース）」の自然な実装表現になる。目的は行数削減そのものではなく、**原状回復しやすい実装状態の維持**である。

## 決定ラダー（第 1 段で止まったら下は見ない）

実装対象に着手する前に、上から順に問う。**最初に成立した段で止める**。

| 段 | 問い | 成立時の行動 |
|---|---|---|
| 1 | **そもそも要るか（YAGNI）** | 投機的機能・未要求の一般化はスキップ。要求に無いものを作らない |
| 2 | **既存コードにあるか** | 既存の helper / util / パターンを再利用。書き直さない |
| 3 | **標準ライブラリで足りるか** | 言語の組込み機能を優先 |
| 4 | **プラットフォームのネイティブ機能で足りるか** | 例: CSS で足りるものを JS で書かない / `<input type="date">` を picker lib で置換しない |
| 5 | **導入済み依存で足りるか** | 新規依存を足す前に既存 package を使う |
| 6 | **1 行で書けるか** | 可能なら 1 行 |
| 7 | **最小限の動くコード** | ここで初めて、動く最小限だけを書く |

### 要求されない抽象化の禁止（ラダーの補則）

- 実装が 1 つしかない `interface` を作らない。製品が 1 つしかない `factory` を作らない
- boilerplate / scaffold の過剰生成を避ける。**足すより消す**を優先し、退屈なコードを賢いコードより選ぶ
- ファイル数は必要最小限に保つ

## 品質ゲート（`MUST`・ラダーより優先）

ラダーは**以下を削る口実にしてはならない**。第 7 段「最小限」は下記を**含んだ上での**最小限を指す。YAGNI でセキュリティ検証を削るのは誤読。

- 信頼境界での**入力検証**
- データ損失を防ぐ**エラー処理**
- **セキュリティ**・**アクセシビリティ**の最低保証（UI を伴う場合は `ui-baseline.rules.md` と併読）
- **人間が明示的に要求した機能**（要求されたものは YAGNI の対象外）

適用順序: **品質ゲート（MUST）→ ラダー（SHOULD）**。両者が競合したら品質ゲートが勝つ。

---

## 締緩の調律（REGIME 連動・当事者性の均質化を防ぐ）

「最良のコードは書かないコード」を全ドメインへ一律 default 化すると、探索・研究・prototype 領域の投機的コードという萌芽を刈りうる。よって本 RL は**固定の常時命令ではなく、REGIME が調律できる条件付きルール**とする。

| ドメイン特性 | 調律 |
|---|---|
| 本番・保守中心（既定） | ラダー標準適用（`SHOULD`） |
| 探索 / prototype / 研究 | 第 1 段 YAGNI・第 6 段ワンライナーを**緩める**（試行の萌芽を刈らない）。品質ゲートは緩めない |
| ライブラリ / 公開 API | 第 2〜5 段（再利用・標準・ネイティブ・既存依存）を**強める** |

L0 spec-architect が対話でドメイン特性を判定し、利用者プロジェクトの REGIME.md にラダー強度を明示する（未指定時は「本番・保守中心」= 標準適用）。

---

## 批判精神の再定置（Ultra を去勢しない）

Ponytail 原典の Ultra モードは「**要求そのものに異議を唱える**」。これは DH の philosophy 第 4 条「開発中に人間へ質問しない」・第 7 条 P1「発案は人間専管」と衝突するため、AI が実装中に要件へ異議を唱える経路としては**採用しない**。

ただし「そもそも要るか」という批判の核まで捨てると、残るのは従順な最小化＝ code-golf に堕す。批判精神は**削除せず再定置**する:

- 実装 AI は第 1 段 YAGNI で「未要求の投機」を静かに刈る（実装内で完結・止めない）
- 要求そのものへの疑義（「この機能自体が不要では」）は AI が独断せず、**タイプ C 献上**（仕様改訂提案・philosophy 第 5 条）または **Council 諮問**へ回す。人間の「そもそも要るか」の判断に接続する

## 適用経路

| 使用者 | 経路 |
|---|---|
| L1 autonomous-dev | 実装ステップで本 RL を読み込み、着手前にラダーを適用。逸脱時は DELIVERY.md に理由を残す |
| L1 independent-reviewer | レビュー観点に「要求されない抽象化・過剰実装」を追加（第 3 条 情報純度の実装面） |
| L0 spec-architect | 環境構築時に本 RL を利用者プロジェクトの `.dh/rules/common/` へ配置し、REGIME でラダー強度を確定 |

利用者は `.dh/rules/common/minimalism-ladder.rules.md` で override 可（`<lang>/` に同名ファイルを置けば言語別に上書き。README.md §override 規約）。
