## 1. Issue概要（GitHub Issue起票用サマリ）

### タイトル案

`[Enhancement] 1→5運用対応：履歴層（history/）の追加設計`

### 背景

dialog-harness は現状 0→1 開発に最適化されており、1→5運用（既存プロジェクトの拡張・保守）で以下の課題が顕在化する：

- **二重管理問題**: コードと仕様の同期コスト
- **意図の属人化**: 「なぜこの実装か」が後から失われる
- **古い資料の残存**: 廃止機能の判別不能
- **車輪の再発明**: 過去の却下案の再提案
- **1→5の引き継ぎ困難**: 人間の記憶に依存した保守

### ゴール

Layer 0⇔Layer 1 ループの中で蓄積されるべきデータを「履歴層」として体系化し、AI主導で管理することで上記課題を解決する。

### 設計原則

- **新スキル不要**。既存3層スキルへの追記で実現
- **AIが書く、AIが読む、人間は承認のみ**
- **フラクタル原則維持**：現在⇄過去の照合パターンを各層に同形で配置
- **GitHub連携は任意拡張**：基本設計は履歴層独立で完結

## 2. 議論の前提（原点確認）

dialog-harnessの根本原則：

| 役割     | 行為                               |
| -------- | ---------------------------------- |
| 人間     | 欲求のドキュメント化に協力するだけ |
| AI（L0） | 欲求を構造化、モード判定           |
| AI（L1） | 自律駆動開発、献上                 |
| 成果物   | 仕様に合う・動く・使える           |

1→5は「献上の繰り返し」。各献上時に蓄積される情報のうち**次回ループの判断材料**になるものを選別・配置する設計問題。

### 追加された原則

ブレストで派生した原則：

> **「気付きは人間、検出・提示・記録・整理はAI」**

> **「人間社会で確立されたプロトコルがある領域は、AIで再発明せず流用する」**

> **「人間にできないがAIにできることを整備する」**（AIの記憶能力を人間の記憶代替として機能させ、人間は意思決定に集中する）

## 4. 履歴層スキーマ

### ディレクトリ構造

```
project-root/
├── (既存ドキュメント群: INDEX.md / SPEC.md / DONT.md / REGIME.md / CLAUDE.md / .claude/ / sensors/)
└── history/                    ← 新設
    ├── SUMMARY.md              ← 自動生成、L0振り返り用
    ├── INTENT.md               ← WHY層（機能の意図、却下案、廃止理由）
    ├── CHANGELOG.md            ← WHAT層変遷（時系列変更記録）
    ├── REGIME-LOG.md           ← 判定層事後評価
    ├── ARCH-DECISIONS.md       ← HOW層判断（任意、ADR形式）
    ├── PATTERNS.md             ← 失敗/成功パターン（任意、自動蓄積）
    └── archive/                ← 古い履歴のアーカイブ
```

### 各ファイルの役割

| ファイル          | 書き手                 | 読み手              | 形式                    | 必須/任意 |
| ----------------- | ---------------------- | ------------------- | ----------------------- | --------- |
| SUMMARY.md        | AI（自動生成）         | L0/L1/reviewer/人間 | 圧縮サマリ              | L≥1で必須 |
| INTENT.md         | L0（対話で抽出）       | L0/L1/reviewer      | 機能ID×意図のマッピング | L≥1で必須 |
| CHANGELOG.md      | L1（献上時自動追記）   | L0（次回対話時）    | 時系列の機能変遷        | L≥1で必須 |
| REGIME-LOG.md     | L1（事後評価から抽出） | L0（次回判定時）    | 判定×実績の対応表       | L≥1で必須 |
| ARCH-DECISIONS.md | L1（実装時記録）       | L1（次回拡張時）    | ADR形式の軽量版         | 任意      |
| PATTERNS.md       | reviewer（検証時抽出） | L1（実装前参照）    | 罠パターン集            | 任意      |

### INTENT.md テンプレ案

```markdown
# 意図ログ

## 機能ID: F001 - カート機能

- **状態**: 現役
- **追加日**: 2026-01-15
- **意図**: 購入意思決定の中断・再開を許容するため
- **条件根拠**:
  - 上限30品 → 平均購入数の3倍を許容（離脱防止）
  - 在庫超過時エラー → UX上の即時フィードバックが目的
- **却下案**:
  - 上限なし: パフォーマンス劣化リスク
  - 在庫予約: スコープ外（DONT.md参照）
- **関連**: F002（決済）, F005（在庫）

## 機能ID: F003 - お気に入り

- **状態**: 廃止 (2026-03-20)
- **廃止理由**: 利用率2%未満、カート機能で代替可能と判断
- **復活条件**: ユーザーリサーチで明確な要望が再度上がった場合
- **廃止合議**: 人間承認、AI状況データ提示
```

## 5. Lifecycle軸の追加

REGIME.mdの判定軸に新たな軸を追加：

| Lifecycle | 値   | 内容                  | 履歴層の扱い                         |
| --------- | ---- | --------------------- | ------------------------------------ |
| L=0       | 新規 | 0→1段階、history/なし | 履歴層は新規作成のみ、儀式スキップ   |
| L=1       | 拡張 | 30日以内の継続開発    | INTENT/CHANGELOG参照を必須化         |
| L=2       | 保守 | 30日超の保守フェーズ  | 全履歴参照必須、reviewerで整合性検証 |

### Lifecycle判定ロジック

```
1. history/ 存在確認
   なし → L=0
2. CHANGELOG.md最終更新日確認
   30日以内 → L=1
   30日超 → L=2
```

**Lifecycle判定はAIが履歴層から自動抽出**。人間に問わない。

## 6. 振り返り儀式の設計

### 4段階の儀式レベル

| レベル | 条件                                       | 処理                      | コスト        |
| ------ | ------------------------------------------ | ------------------------- | ------------- |
| 0      | history/なし、または前回ループから経過なし | スキップ                  | ゼロ          |
| 1      | 30日以内、規模変化なし、L=1                | SUMMARY.mdのみ、1問確認   | 最小（~30秒） |
| 2      | 30日超 or 機能追加/変更含む対話            | SUMMARY+関連INTENT、2-3問 | 中（~3分）    |
| 3      | L=2保守 or 90日超 or 規模変動±2以上        | history全層、5-10問       | 大（~15分）   |

### 儀式の動的格上げ

| 検出シグナル             | 格上げ |
| ------------------------ | ------ |
| 過去INTENTと矛盾する欲求 | 1→2    |
| 廃止機能の復活要求       | 1→2    |
| 却下済み案の再提案       | 1→2    |
| 大規模リファクタの示唆   | 2→3    |
| 規模判定がL2閾値接近     | 強制3  |

### 儀式の動的格下げ

| 検出シグナル                       | 格下げ |
| ---------------------------------- | ------ |
| 履歴層がほぼ空（INTENT 3件以下）   | 2→1    |
| 人間が明確に「軽くやりたい」と発話 | 2→1    |
| 純粋なバグ修正のみで仕様変更なし   | 1→0    |

### 儀式の3フェーズ（実行時）

**F1: 過去文脈サマリ提示（AI主導）**

- 履歴ロード
- 提示用サマリ生成
- 人間に「認識合ってますか？」

**F2: 認識ズレ検出（AI主導）**

- 新欲求×過去INTENT照合
- 矛盾/復活要求/再提案の検出
- 検出時のみ人間に確認

**F3: 履歴更新予告**

- 対話で確定した更新内容を宣言
- 人間が承認/修正

### 形骸化防止メカニズム

1. **儀式実行ログをREGIME-LOG.mdに記録**（儀式自体も履歴）
2. **儀式スキップが連続したら警告**（5回連続でレベル2推奨）
3. **儀式効果を体制事後評価に記録**（検出件数、手戻り回避効果）

## 7. 廃止判断プロトコル

### 役割分担

| フェーズ     | 主体            | 内容                                     |

| 不満発生     | 人間のみ        | 成果物使用→不満を抱く                    |

| 廃止記録     | AI              | INTENT.mdに廃止マーキング、復活条件記載  |

### 廃止候補検出のデータ源

## 8. 履歴更新承認の3段階

### 承認レベル

| レベル      | 対象                                            | 人間対応                 |
| ----------- | ----------------------------------------------- | ------------------------ |
| A: 自動承認 | CHANGELOG追記、ARCH-DECISIONS追記、PATTERNS追記 | スキップ可、通知のみ     |
| B: 確認推奨 | INTENT新規追加、REGIME-LOG事後評価              | 一覧確認、無修正で承認可 |
| C: 必須承認 | INTENT廃止マーキング、却下案追加、Lifecycle変更 | 個別承認、修正可能       |

### 判定基準

- **A**: 履歴層内で完結する追記、過去判断と矛盾しない
- **B**: 新規記録だが将来判断に影響、破棄しても復元容易
- **C**: 過去判断の上書き/否定、または将来制約となる記録

### REGIME.mdの承認設定例

```markdown
## 履歴更新承認設定

- レベルA（自動承認）: スキップ
- レベルB（確認推奨）: 通知のみ、デフォルト承認
- レベルC（必須承認）: 必ず確認
```

### DELIVERY.mdの履歴層更新差分セクション例

```markdown
## 履歴層更新差分

### レベルA（自動承認済み）

- CHANGELOG.md: F010追加、F001条件変更
- ARCH-DECISIONS.md: 通知ライブラリ選定

### レベルB（確認推奨）

- INTENT.md: F010の意図記録（下記参照）
- REGIME-LOG.md: 第4回判定の事後評価（下記参照）

### レベルC（必須承認）

- なし

### 詳細

[各更新内容の全文]
```

## 9. 訂正プロトコル

### 認知の3系統

| 主体                 | 認知タイミング | 検出方法               |
| -------------------- | -------------- | ---------------------- |
| 人間                 | L0対話中       | 「あれ、これ違うかも」 |
| L0 spec-architect    | 振り返り儀式中 | 新欲求×過去INTENT照合  |
| independent-reviewer | 検証時         | 実装×過去INTENT照合    |

### 判定プロトコル（合議＋エビデンス）

```
1. 検出側が「間違いの可能性」を提示
   - 何が間違いか
   - 根拠データは何か
   - 現状の事実は何か
2. 人間が判定
   - 間違いと認める → 訂正へ
   - 間違いではない → 異なる解釈として両論併記
   - 判断保留 → 次回ループに持ち越し
3. AIが訂正記録を作成
   - 人間が承認
```

### 訂正記述方式（取り消し線＋理由併記）

| 要素     | 内容                     |
| -------- | ------------------------ |
| 旧記述   | 取り消し線で残す（証跡） |
| 新記述   | 太字で訂正部分を明示     |
| 訂正日時 | いつ訂正したか           |
| 訂正理由 | なぜ訂正したか           |
| 検出主体 | 誰が間違いに気付いたか   |
| 合議結果 | 誰が承認したか           |

### カスケード対応

```
1. 訂正実施時、AIが波及範囲を自動検出
   - INTENT.md内の関連機能
   - CHANGELOG.mdで該当機能の変更履歴
   - REGIME-LOG.mdで該当機能を含む判定
2. 波及候補を人間に提示
3. 各波及先について個別判定
4. 全波及処理を1つの「訂正セッション」としてREGIME-LOG.mdに記録
```

### 緊急訂正

sensors側に「重大変更検出」を組み込み、L0対話を強制起動。
ただし最終判断は必ず人間。

```markdown
## 開発環境連携

- 連携時の方針: 履歴層を一次情報源とし、GitHub artifactsは派生として扱う

- history/INTENT.md → 関連Issue自動リンク

```

## 13. 議論の経緯（参考）

### 議論の起点

AIコーディング保守運用の動画議論から以下の課題を抽出：

4. AIの普及が生んだ車輪の再発明と管理崩壊
5. 今後の保守運用に向けたアイデア（生存競争型運用）

### 議論の流れ

| ターン | 内容                                           | 結論                                   |
| ------ | ---------------------------------------------- | -------------------------------------- |
| 1      | 動画議論からの示唆抽出                         | INTENT保存、Lifecycle軸の追加が最優先  |
| 2      | 1→5はLayer 0⇔Layer 1ループの履歴層問題と再定義 | スキル化ではなく情報配置の問題         |
| 3      | 履歴層の蓄積要素・配置・参照方法のブレスト     | history/独立配置、フラクタル原則維持   |
| 4      | 論点A確定（AI責務、振り返り儀式必須）          | 「人間にできないがAIにできること」原則 |
| 5      | GitHub連携の検討                               | 任意拡張として確定、基本は独立設計     |
| 6      | 論点G/H/I確定                                  | 連携拡張、自動マージ、Git管理する      |
| 7      | 論点E（儀式コスト）確定                        | 4段階レベル+動的格上げ/格下げ          |
| 8      | 論点B/D確定                                    | 廃止は合議、承認は献上単位3段階        |
| 9      | 論点F確定                                      | 人間社会方式の流用、取り消し線方式     |

| ボツ案                               | 不採用理由                                 |
