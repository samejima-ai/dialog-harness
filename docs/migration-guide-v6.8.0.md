# migration-guide v6.8.0 — CLAUDE.md 統括者モデルへの移行

対象: 旧規格（エージェント RL = 原則 / コーディング規約 / 禁止事項 / 参照 の平置き集積）で運用中の既存プロジェクトを、
プロジェクト統括者モデル（純化された常駐 + ルーティング表 + ゲート強制 3 段）へ移行する手順。

- 正本: `templates/rules/common/claude-md-purity.rules.md`（v0.2.0）+ `dev-env-spec.md` §CLAUDE.md
- **移行は任意**。CLAUDE.md は dh-manifest の never_touch であり、DH 更新は既存 CLAUDE.md を書き換えない。
  移行は利用者プロジェクト側の独立 PR として、人間の明示指示 + 承認の下で行う
  （プロジェクトが CLAUDE.md を人間専管〔例: kakuman の L-FROZEN-META〕に指定している場合は特に必須）。
- 第一適用例: kakuman-platform v3.0（メタ診断 2026-08-04 起点）。

---

## 手順（6 ステップ・atomic 1 PR）

> **atomic 原則**: ステップ 2〜6 の成果は**必ず同一 PR** に入れる。分割すると中間状態で
> lock-step sensor FAIL / 規範の宙吊り（索引からも所有元からも見えない状態）が発生する。
> 全変更は docs + scripts に閉じる（DB / migration / 本番に触れない）ため `git revert` 1 発で原状回復できる。

### 1. 診断

- サイズ実測: `wc -c CLAUDE.md` / `LC_ALL=C awk 'length($0)>400' CLAUDE.md`（配置 drift センサーと同じ式。`LC_ALL=C` を省くとロケールにより文字数計測になり byte 閾値とずれる）
- 参照実在: CLAUDE.md が引用する全パス・アンカーの実在確認（broken reference）
- lock-step 同期: 既存の索引 ⇄ 所有元の同期検査（例: kakuman `check-traps-sync.mjs`）を実行
- 自己規範違反: CLAUDE.md 自身が定める必須手順（マトリクス追記等）の履行漏れを検出
- **機械依存の洗い出し（必須）**: `grep -rn "CLAUDE.md" scripts/ sensors/ .github/ .claude/` で
  CLAUDE.md の**構造を parse する**スクリプト・センサー・workflow を列挙する。
  構造依存が見つかったら、その改訂を本移行 PR のスコープに含める
  （kakuman 先例: `check-traps-sync.mjs` が索引の罠 ID 集合を parse しており、索引移動と同時改訂が必要だった）

### 2. 分類

全規範を 3 分類する。判定基準は純化 RL §3（到達可能性）:

| 分類 | 判定 | 行き先 |
|---|---|---|
| 常時規範 | CLAUDE.md から消したら grep 到達前に事故る | 常時規範セクションに索引 1 行で残す |
| 領域規範 | 特定領域を触るときだけ効く | ルーティング表の 1 行（gate ID 付き）へ。実体は所有元 |
| 経緯・実体 | provenance / 詳細手順 / 他文書の再説明（純化 RL §1 ②③） | 所有元（SPEC / DONT / docs / history）へ移送 |

- 事故時被害が大きい規範（破壊的操作・認可漏れ）は、領域規範でも per-規範 1 行を常時側に残してよい（純化 RL §7 の併用許容）
- **add-demote-check** をこの時点から適用開始する

### 3. 移送

- 経緯・実体を所有元へ（既に所有元にある場合は CLAUDE.md 側を索引 1 行へ縮約するだけ）
- 領域規範の実体が所有元に不在なら、先に所有元へ本文を書いてから索引を落とす（宙吊り禁止）

### 4. 再構築

- 統括者フォーマット（Identity / 常時規範 / ルーティング表 / 参照）で CLAUDE.md を再編
- ルーティング表の各行に gate ID（`G-` prefix）を付与

### 5. 配備（すべて実行主体ローカル）

- 配置 drift センサー + ルーティング突合センサーを `scripts/` に配置し `sensors/computational.md` へ登録
- 既存 lock-step sensor を新構造に合わせて改訂（手順 1 で列挙した機械依存の同時改訂）
- DELIVERY.md テンプレ（またはプロジェクトの PR テンプレ）に「通過ゲート記録」欄を追加
- Actions が無効なプロジェクトでは、マージ前ローカルレビュー手順に「diff × ルーティング表の突合 + 通過ゲート記録の確認」を組み込む（CI にしか存在しない検査を作らない）

### 6. 検証

- byte 実測（センサー PASS 確認）/ broken reference 再検査 / lock-step sensor PASS
- 移行前後で「規範の総数が不変」であることを確認する（純化は移送であって削除ではない。
  意図的に廃止する規範がある場合は別途、廃止判断プロトコルを通す）

## 段階適用オプション

一括移行のレビュー負担が大きい場合、2 段に分けてよい（各段は上記 atomic 原則を満たすこと）:

- **第 1 段**: 領域規範の移送 + ルーティング表新設 + センサー配備（変更が「禁止事項」相当セクションに閉じ、削減効果が最大）
- **第 2 段**: 常時規範セクションの再編（原則 / コーディング規約の索引 1 行化・②③の摘出）

---

## 移行しない選択

罠索引型（per-規範 1 行常駐）のまま純化 RL v0.1.0 準拠で運用し続けることは正当な選択である
（ゲート強制 3 段を持たないプロジェクトはむしろ罠索引型を維持すべき — 純化 RL §7）。
その場合も手順 1 の診断（特に ②③ の混入検出）と §2 二重定義禁止は適用を推奨する。
