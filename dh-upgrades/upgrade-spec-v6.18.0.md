## 0. 位置づけ — 検知器を増やさず、時限を読む主体を置く

v6.17.0 は「宣言 → 実体」の片肺だった検査に「実体 → 宣言」「宣言の鮮度」を足した。
本 spec が扱うのはその次の層である — **宣言された時限（`review_trigger`）を読む主体が居ない**。

`review_trigger` は v6.13.0 で導入され、以来 23 ファイルが宣言してきた。しかし
「期限が来たかを判定して人間に問う」経路は `signal-scan.yml`（90 日の日数近似）しか無く、
`cycles: N` / `stage_transition:` / `measured:` といった宣言形式は**誰も読んでいなかった**。
書いた本人（DH）が読まない宣言は、書いた瞬間から静かに失われる。

### 静かな失敗の 3 型（`delivery/ANALYSIS-silent-failure-2026-09-06.md`）

| 型 | 定義 | 検出可能性 | 本 spec の対応 |
|---|---|---|---|
| **A** | 宣言と実体の乖離 | 決定論的に検出可能 | v6.17.0 F1-F6 が担当。**§F0 で自己適用の破れを是正** |
| **B** | 時間減衰による停止 | 検出可能（日数・cycle 数） | **C-1**: `norm-scan.py` が読む主体になる |
| **C** | 配線されているが導通していない | **原理的に検出不能**（「通った」痕跡が無い） | **B-1**: 期限条項付きの点検を回す（検知器を作らない） |

型 C に検知器を作れないのは、痕跡を記録する機構そのものが静かに死にうるからである（無限後退）。
よって対策は「定期点検 + その点検自体に有効期限を付ける」となる。

## F0. 版番号の自己適用 — 本 spec の不在そのものの是正

### 現況（2026-09-07 実測）

| 対象 | 実測値 |
|---|---|
| `VERSION` | `6.17.0` |
| `dh-upgrades/upgrade-spec-v6.18.0.md` | **不在**（本ファイルが是正） |
| v6.18.0 を名乗るコミット | `5299099`（#264「v6.18.0 C-2」） |
| 検査 9（宣言の鮮度）の結果 | **PASS** |

検査 9 は `VERSION` ⇄ `GRAPH.yml version:` ⇄ upgrade-spec の状態行を突合するが、
**コミットメッセージが名乗る版番号は見ない**。ゆえに乖離は PASS のまま通過した。

### 判断 — 検査を足すか、足さないか

**足さない。** コミットメッセージを検査対象にするには、

- 検査 9 が git 履歴を読む必要がある（現在は作業ツリーのみ。I-5「検査はローカルで走る」と両立するが結合が増える）
- squash merge でメッセージが書き換わるため、検査時点と ship 時点でメッセージが異なりうる
- 「版番号を名乗ったコミット」の定義が正規表現依存になり、I-3（決定論）を満たしても偽陰性が読めない

以上より、機構ではなく**手順**で閉じる。実装着手時に spec を先に置く、が既存の L0 手順であり、
本件はその手順を私が飛ばしたことによる。手順の不履行に検知器を足すのは I-4（常時発火する検知器を
作らない）と TR-4（常時発火する検知は形骸化する）に触れる方向である。

### 是正

1. 本 spec ファイルを置く（本コミット）
2. `VERSION` は **6.17.0 のまま据え置く**。C-3 の実装完了時に 6.18.0 へ昇格させる
   （実装中に VERSION を上げると検査 9 の「実装済みを名乗る版が VERSION を超える」検査と衝突する）
3. 状態行に C-1 / B-1 / B-3 / C-2 を「済」、C-3 を「起草中」と明記する（本ファイル冒頭）

### 規範メタデータ

```yaml
stage: 全段階
review_trigger:
  - measured: 版番号を名乗って spec 無しで ship する事象が再発したら、F0 の「手順で閉じる」判断を再問する
```

## C-1. 時限メタデータを読む主体 — `scripts/norm-scan.py`（実装済み・PR #261）

### 解いた問題

`review_trigger` の宣言形式は 4 種（`date:` / `cycles: N` / `stage_transition:` / `measured:`）あるが、
`signal-scan.yml` は最終 commit からの日数近似しか見ておらず、他 3 形式は誰も読まなかった。

### 実装

- `date:` / `cycles: N`（14 日近似）/ `stage_transition:` を決定論で判定する
- `measured:` は**列挙のみ**（I-3: 検知は決定論。人が測る条件を機械が判定してはならない）
- **非発火・判定不能も記録する** — 「走査が見落とした」と「判定して発火しなかった」を区別するため
- 除外は `dh-upgrades/` `history/` `delivery/`
- `ritual-protocol.md` F2.6 から起動される

### 実測（2026-09-07）

22 トリガー / 25 行を検出。うち `measured` が大半で、機械判定は行わず儀式で人間に問う形。

### 規範メタデータ

```yaml
stage: 全段階
review_trigger:
  - measured: 検出トリガー数が 3 cycle 連続で増減 0 なら、規範の時限宣言自体が止まっている可能性を疑う
```

## B-1. 点検にリズムを与える — 期限条項付きの点検（実装済み・PR #262）

### 解いた問題

型 C（配線されているが導通していない）は原理的に検出不能である。検知器を作ると、
その検知器自身が静かに死にうる（無限後退）。

**私自身が型 C を犯していた**: `council-ctl.py export` を「毎回必須」と実装・文書化しながら
一度も走らせず、`.council-ctl.json` が 2 日間 stale だった。

### 実装

`dev-env-spec.md` に「## 点検」節を追加。60 日を下限とし、**点検規範自体に有効期限条項**を置いた。

### TR-4 の正確な読み（諮問時の私の誤引用を是正した記録）

Council ブリーフで私は TR-4 を「新しい常駐機構を作らない」と要約したが、哲学者軸が一次ソースから
訂正した。原文は `telemetry-reflux.rules.md:22`:

> **TR-4 常時発火する検知は形骸化する**。検知器は絞って始め、実測 1 ヶ月で見直す

これは常駐機構の禁止ではなく、**形骸化の法則 + 期限による救済**である。この訂正により、
期限条項は「あれば良いもの」から**遵守要件**へ格上げされた。

### 規範メタデータ

```yaml
stage: 全段階
review_trigger:
  - date: 2026-11-06
  - measured: 点検が 2 回連続で「是正すべきもの無し」なら、点検自体の間隔を延ばすか廃止を検討する
```

## C-2. 検査 8 の分割 — 欠落の型で切る（実装済み・PR #263 / #264）

### 解いた問題

検査 8（`declaration_coverage.py`）が v6.17.0 で 6 → 13 項目に増え **672 行**に肥大した。

決定的だったのは行数ではない。Council 諮問（`splt02`）で **3 軸すべてが独立に同一のバグを発見した** —
dict リテラルに `location` / `message` が重複し、Python の後勝ちで **F4 の計数が F3 に上書きされて
出力から消えていた**。検査 8 のラベルは「F4 分類網羅」と名乗るのに計数行が無い状態が続いていた。

**検査器が、自分が検出すべき型の欠陥（型 A）を持っていた。**

混入元は PR-F の rebase で 5 箇所の衝突を解決した際、独立検証が「両方を残す」と助言した箇所を
dict の中で機械連結したこと。#263 で是正し、`ast` による重複キー検査を回帰テストに追加、
変異注入で検出能力を実証した。

### 分割基準の改訂

申し送りにあった「1 検査器 = 1 宣言ファイル」は**実測で実態と合わなかった** —
F1 は 4 ファイル、F4 は 2 ファイルを読み、F3 は宣言を読まない（実体走査のみ）。

採用した基準は **「1 検査器 = 1 つの欠落の型」**:

| モジュール | 欠落の型 | 行数 |
|---|---|---|
| `declaration_freshness.py` | 鮮度 — 宣言が実体に追いついているか | 181 |
| `declaration_coverage.py` | 実体→宣言 / 宣言の実質 | 341 |
| `distribution_state.py` | 実体の誤配置 | 104 |
| `rules_index.py` | 実体→宣言（RL 索引） | 99 |

> **予約された基準は実装前の視界で書かれる以上、実装後の実態と食い違いうる。
> 予約を「そのまま従う指示」ではなく「再考の契機」として扱う。**

### 必須随伴条件（5 点・すべて充足）

1. **検査番号を付け替えない** — `reports/*.md` 5 本は過去の実行記録であり、書き換えは改竄になる。
   `CHECK_REGISTRY` を安定 ID 付き 3-tuple に改め、分割モジュールは末尾追記して 1-7 を不変に保った
2. `parse_graph` の ImportError fallback を `checks/_declaration_util.py` へ集約（複製禁止）
3. 回帰テストの件数の前後一致（43 ケース）+ 共通 fixture `scripts/_verifier_fixture.py`
4. 基準改訂の理由を spec に明記（本節）
5. 分割と**同時に** 13 項目の発火実績を棚卸し（12 項目に実績あり。空の器の整理ではなかった）

### 規範メタデータ

```yaml
stage: 全段階
review_trigger:
  - measured: いずれかのモジュールが 300 行を超えたら、欠落の型がさらに分岐していないか再問する
```

## C-3. 配布先検査の還流 — 決定待ち文書の制度化（起草中）

### 現況（2026-09-07 実測）

`delivery/UPSTREAM-DECISION-2026-08-26.md` は kakuman から DH へ還流させる候補 7 機構を
推奨順に並べた決定シート。冒頭に「**人間が答えるのは 1 問だけ**: 上から何件採るか」と明記され、
末尾の記入欄「採用件数: 上から ____ 件」は **12 日間空欄のまま**である。

その 12 日の間に、**7 件中 3 件がシートを読まれないまま別経路で実装された**。

| 項目 | シートの記述 | 2026-09-07 実測 |
|---|---|---|
| 1. 領域ゲートの述語化 | 未着手（推奨 1 位） | 未着手（`GRAPH.yml` に `predicate` 0 件） |
| 2. 規範の分割不変条件 | 未着手・**「1 に依存する」** | **実装済み**（v6.17.0 F6 → #264 で独立モジュール化）。しかも**項目 1 に依存せず**着地 |
| 3. 観測層の非ゲート化 | 未着手 | **実装済み**（`signal-scan.yml`。思想がファイル冒頭にそのまま書かれている） |
| 4. 配置と武装の分離 | 未着手 | **未採用**（cron は日次で有効。消費枠の判断が AI 側に移った状態） |
| 5. 武装解除の明示 fail | 「`upstream-scan.py` に自己適用済み」 | 同左（規範化のみ未） |
| 6. 購読量の CI 強制 | 未着手 | 未着手（`scripts/` に size 検査なし） |
| 7. 不可逆操作の deny 強制 | **「DH 本体には `.claude/settings.json` が存在しない」** | **ファイルは存在する**（#209 で新設）。ただし `permissions` 節が無い |

### 制度的原因 — 決定待ち文書は制度の外に落ちる

`norm-scan.py:58` は `delivery/` を「分析・献上物。規範ではない」として時限走査から明示除外している。
**決定シートは時限検知の死角に置かれていた。**

`ANALYSIS-silent-failure-2026-09-06.md` §7 が「本分析も静かに失われうる」と自ら書いた予言は、
同じディレクトリの隣のファイルで**既に成就していた**。

さらに走査の母集合が 2 機構で分裂している:

| | `norm-scan.py`（C-1） | `signal-scan.py`（v6.15.0） |
|---|---|---|
| 拡張子 | `.md` `.py` `.yml` `.yaml` | `.md` `.yml` `.yaml`（**`.py` 無し**） |
| 除外 | `dh-upgrades/` `history/` `delivery/` | **無し** |

私が C-1 で `.py` を足したことにより、`signal-scan` が **検査モジュール 7 件の期限宣言を
見落とす**状態が生まれた（#264 で分割した 4 モジュールを含む）。

### 空欄 12 日は型 A/B/C のどれか — **第 4 の型**

型 A-C はすべて機構の側の不作動を見ている。本件は**機構が正常に動作し、正しく人間に届き、
それでも動かない**。原因は不作動ではなく問いの形式の誤りであり、検知器では原理的に拾えない。

これを型 B（時間減衰）と誤診すると「催促を自動化する」という最悪の対処に流れる。

### 判断点 — Council `upst03`（jc 0.78）

`weighted_score` は B（先行実装）が 6.56 対 2.16 で支配的だったが、**判定は B をそのまま採らない**。

開発者軸は B の技術的前提を実測で確認した — `dh-manifest.yml:81-83` が `.claude/settings.json` を
**`merge` 分類**（`overwrite` ではない）と宣言しているため配布先へ raw 上書きされず I-6 と衝突しない。
`permissions.deny` の追加は単一 JSON キーで、削除により完全復旧する最高可逆性の変更である。

しかし哲学者軸がその前提を否定した:

> 7 件中 3 件が既に別経路で消えている以上、残りも AI が削れば、
> 人間が答えるべき問いは消滅によって解決されたことになる。
> それは第 6 条の充足ではなく回避である。

**可逆なのは実装であって、問いの消滅は可逆ではない。** よって B の実装部分は人間の採否回答後へ繰り延べる。

### 必須随伴条件（5 点）

1. **設問形式を改める** — 「上から何件」→「項目ごとに 採用 / 保留 / 還流済み」。
   実測で順位下位の項目 3/4 が先に実装され上位の項目 1 が残っており、**順位という前提が成立していない**
2. **項目 2/3/4 を「還流済み」として表から抜き、どの経路で還流したかを 1 行残す**。
   これは訂正ではなく、**還流が順位表を迂回した記録**である
3. **決定シートに規範メタデータを付与する** — 現在まったく無い。
   人間の判断待ちという最も期限管理を要する文書が、期限宣言を持っていなかった
4. **`norm-scan.py` の `delivery/` 一律除外を見直す** — 「規範ではないから除外」の線引きは正しいが、
   **決定待ち文書は規範ではないのに腐る**。この第三のカテゴリが制度の穴である
5. **`signal-scan.py` の `review_trigger` 母集合に `*.py` を追加する** — 上記の分裂を閉じる

### 採らなかった選択肢

- **D（決定シートを廃し signal-scan の検知対象へ移す）**: 3 軸が独立に否定。
  `signal-scan.yml` ヘッダ自身が記録する F8 事故（日次 cron で dedup が外れ 2026-08-28〜09-05 に
  同一 3 PR で 27 件の重複 Issue）が I-4 / TR-4 違反を実証し、`dh-manifest.yml` U-4 が upstream 走査に
  「存在差分の列挙に閉じる・優劣判定はしない」を課しているため順位を検知器へ移すこと自体が U-4 違反。
  哲学者軸曰く「**還流候補は信号ではなく記憶であり、常時観測に載せると毎日思い出させられることで摩耗する**」
- **C（凍結）**: 実態と乖離した文書を乖離したまま次サイクルへ持ち越す点で保守性上最悪

### 記入欄への代筆は行わない

philosophy 第 6 条の遵守としてだけではない。哲学者軸の指摘:

> この空欄が現在 DH の持つ最も価値ある観測データである。
> 空欄は失敗の記録ではなく、**形式が意味を運び損ねたことの唯一の痕跡**である。埋めれば消える。

### 規範メタデータ

```yaml
stage: 全段階
review_trigger:
  - date: 2026-10-07
  - measured: 設問形式を改めた後も 30 日以上記入されなければ、順位表という形式自体の廃止（哲学者軸の「出来事カード」案）を再問する
```

## 保留（本 spec の射程外・独立議題）

| 論点 | 出典 | 理由 |
|---|---|---|
| 順位表を廃し 1 件 = 1 出来事カードへ解体する | `upst03` 哲学者 notes | 決定シート更新後の実測（人間が新設問に答えるか）で検証すべき |
| 還流一般に適用できる規律としての規範化 | `upst03` 開発者 notes | C-3 の実測を経てから |
