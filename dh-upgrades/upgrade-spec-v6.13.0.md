## 0. 位置づけ — 新機構ではなく「既存宣言への実行経路」

前 cycle で観測された 4 件の失敗は、独立した 4 つの不具合ではなく **1 つの形の 4 つの現れ**だった。

> 規範に書いてある。しかし **AI が思い出さなければ何も起きない**。

本リリースは新しい判定機構・新しい規範カテゴリを **追加しない**。既に規範として存在する宣言
（opt-in 領域 / 役割分離 / 事後評価 / 時限メタデータ）に、AI の記憶に依存しない実行経路を与える。
f5fc45「減らす・時限化」原則との整合: 規範量は増やさず、**既存規範の実効性のみを上げる**。

本サイクルで新たに観測された 5 件目も同型である（§F3 起点）。振り返り儀式 F2.5 で人間が下した
事後評価 3 件は正しく記録されたにもかかわらず、`decision_category` が空欄であるという理由で
**警告なく集計から捨てられた**。前 cycle の #3（行末コメント書式でパーサが評価を落とした）と同じ形が、
別の機構でもう一度出た。

### 不変条件（全機能共通）

- **I-1 境界の値を動かさない**。`auto-merge-boundary.md` は philosophy 第 9 条の **L-FROZEN-META**。
  本リリースは当該ファイルを **読むだけ**であり、1 バイトも書き換えない。改訂が必要と判明した場合は
  人間へ献上し、AI は提案 PR も作らない
- **I-2 `philosophy.md` に触れない**（L-FROZEN-PHIL、2026-11-06 の評価ゲートまで）。第 1 条・第 3 条の
  条文は動かさず、条文が既に要求している内容に実行経路を与えることのみを行う
- **I-3 隔離は人間ゲートを消さない**。機械隔離（§F1）を既定にする前に、その隔離下で実行不能になる
  人間ゲートを機械側へ移し終えていること。**§F2 は §F1-1 の前提条件であり、順序を逆にしてはならない**
- **I-4 検出器は黙って捨てない**。集計・検査の対象外とする判断を下したら、件数と対象を必ず可視化する。
  silent skip は「検査が通った」と読める点で無検査より悪い
- **I-5 宣言と計数器は同一 PR で着地させる**。受け入れ基準・時限・閾値を新規に宣言する PR は、
  それを数える経路を同じ PR に含める。含められないなら宣言しない
  （v6.12.0 開発者軸 少数意見の一般規則化。当時の実測: `review_trigger` 系の宣言は 7 文書、対応する計数器は 0 個）

## F1. 第 1 層・独立検証の隔離実行（priority: critical）

役割の**時間的分離**を運用規律ではなく実行形態で担保する。philosophy 第 3 条 §独立コンテキスト必然性が
挙げる例（実装者 vs レビュアー）は**空間的分離**を射程とし、同一エージェントが第 0 層を演じたあと
第 1 層を演じる時間的分離を含んでいなかった。条文は動かさず、実行形態でこれを埋める。

| 条件 | 内容 |
|---|---|
| F1-1 | 第 1 層（`layer1-autonomous-dev`）と独立検証（`layer1-independent-reviewer`）は**既定で隔離実行**。v6.11.0 の実行基盤（Workflow / subagent）に載せ、本流セッションのコンテキストを継承しない |
| F1-2 | 隔離実行が使用不能な場合の**退避経路**は別セッション運用（第 0 層が献上した時点でセッションを閉じ、第 1 層は新しいセッションで受領する）。degrade するが停止しない（v6.11.0 F6-4 と同型） |
| F1-3 | 同一セッションでの 第 0 層 → 第 1 層 連続実行は**逸脱**として扱う。禁止はしない（人間が選べる）が、DELIVERY に逸脱として記録する |
| F1-4 | **隔離下では第 1 層の人間ゲート 2 点を機械経路で担保する**。§7.5 opt-in 判定は §F2 が、H カテゴリ抵触の即時献上は既存の escalation-matrix が担う。**§F2 未着地の状態で F1-1 を既定にしてはならない**（I-3） |
| F1-5 | 独立検証の隔離は新規則ではなく、v6.11.0 I-4（Workflow journal を reviewer の入力に含めない＝実装コンテキスト隔離）の実行経路化である |

**なぜ機械隔離を主、別セッションを退避とするか**（L0 対話決定）: 別セッション運用は人間と AI 双方の
記憶に依存する。今回閉じようとしている欠陥がまさに「記憶に依存した規律は落ちる」であり、
同じ形の対策を採れば同じ形で破れる。ただし隔離実行が使えない環境は実在するため退避経路を残す。

**v6.11.0 との関係**: v6.11.0 は Council / review / 反証 / L2 / L0 ブレストに実行基盤を与えたが、
**第 1 層本体だけが対象外**だった。本 F1 はその穴を埋める。新規基盤は作らない。

## F2. opt-in 境界の導出型配線（priority: critical）

「規範文書を auto-merge の停止条件に加えよ」という Council `f9b2c4` の是正は、escalation-matrix の
**促しの表**に書かれたまま機械化されていない。GRAPH.yml には既に該当エッジが宣言されている
（`auto-merge → human-P4-停止介入` / condition: opt-in 領域に該当）。**宣言は済んでいて、配線だけが無い。**

### 実装先の切り分け（起点文書 §4 の前提を訂正する）

`ANALYSIS-role-boundary-2026-08-25.md` §4 は候補 B を「人間が手で書く以外に実装経路がない」としたが、
これは実装先を `auto-merge-boundary.md` と見なしたことによる。実際には両者は別物である。

| 対象 | 役割 | 委譲レベル | AI の可否 |
|---|---|---|---|
| `auto-merge-boundary.md` §opt-in 領域 | 境界の**定義**（何が opt-in か） | **L-FROZEN-META** | 提案 PR も不可 |
| `.github/workflows/auto-merge.yml` | 境界の**執行**（どう止めるか） | opt-in 領域（`human-review-needed` 付与） | **可**（人間レビュー必須） |

境界の定義を読んで執行経路を導出することは、境界を動かすことではない。

| 条件 | 内容 |
|---|---|
| F2-1 | `auto-merge-boundary.md` §opt-in 領域 の表を**読み取り専用**で解釈し、paths パターンと非 paths 条件を導出するスクリプトを新設する。境界表が**単一情報源**であり、導出結果はキャッシュしない |
| F2-2 | 導出結果を auto-merge の停止判定へ接続する。opt-in 領域に該当する PR は、stop ラベルの有無に**よらず** merge しない（ラベル付与は AI の発話に依存するため、依存を断つのが本 F の目的） |
| F2-3 | 乖離検査: 境界表に行が増えたのに導出が追随していない／導出が表に無い条件で止めている、を検出して FAIL にする |
| F2-4 | **`auto-merge-boundary.md` を 1 バイトも変更しない**（I-1）。表の書式が機械解釈に耐えない場合、書式変更を人間へ献上し、AI は書かない。**この場合 F2 は着地せず、したがって F1-1 も既定にできない**（I-3 の連鎖） |
| F2-5 | **本仕様の実装 PR** は「autonomous-drive workflow 自身の改修」＝ opt-in 領域に該当するため、**`human-review-needed` を付与**して人間レビューを通す。これは §opt-in 領域の自己適用である |

**paths で表せない条件の扱い**: §opt-in 領域 8 行のうち「不可逆操作」「Council 低 confidence」等は paths で
表現できない。本リリースは **paths で機械判定可能な行のみ**を配線し、残りは「機械判定不能」として
明示的に列挙・出力する（I-4）。全件を機械化したふりをしない。

## F3. 事後評価の取りこぼし封じ（priority: critical）

`scripts/council-ctl.py` の集計（`_compute_stats`）は、評価済みの判定であっても `decision_category` が
`VALID_DECISION_CATEGORIES` に無ければ `continue` で捨てる。**分母にも分子にも入らず、ログも出ない。**

```python
dc = rec.get("decision_category")
if dc not in VALID_DECISION_CATEGORIES:
    continue                       # ← silent skip
```

2026-08-25 の振り返り儀式 F2.5 で人間が下した事後評価 3 件は、この経路で消えた。
CTL 昇格の律速は事後評価であり、その燃料が黙って捨てられる構造は CTL 設計の前提を壊す。

| 条件 | 内容 |
|---|---|
| F3-1 | 評価済みだが集計対象外となった判定を **silent skip しない**。件数と invocation_id を stderr に WARN として出力する |
| F3-2 | `status` / `recompute` の標準出力に「評価済み N 件 / うち集計対象外 M 件」の行を**常設**する。数字の乖離が常に見える状態にする |
| F3-3 | **分類の機械導出は行わない**。`category`（重み軸）→ `decision_category`（委譲軸）の機械導出は Council `council-2026-07-01T-ctlrec1` で却下済みであり、本リリースはこれを尊重する。空欄 5 件への分類付与は人間判断とし、AI は候補提示に留める |
| F3-4 | 事後評価の**永続先は追跡対象の `history/COUNCIL-LOG.md`**（`implementer_consent`）であることを明記する。`~/.claude/council-data/` は user-scope の導出であり、コンテナ再作成で消える。`council-ctl.py evaluate` のヘルプと儀式 F2.5 手順に、台帳への書き戻しを明示する |

**本サイクルでの実地確認**: F3-4 の欠落は本サイクルで実際に踏んだ。儀式 F2.5 で 3 件を評価した直後、
`git status` が空であることから user-scope 側にしか書かれていないと判明し、`COUNCIL-LOG.md` の
`implementer_consent` へ書き戻して永続化した（5v4xqq / vbxdnd = `agreed_with_modification`、
tmplsync = `agreed_recommended`）。書き戻し後も一致率は 0.875 のまま動かず、F3-1 の silent skip が
現に効いていることが確認された。

**さらに 3 例目**: その書き戻し自体が、同期経路の読まないフィールド名（`evaluated_at` / `evaluation_note`）を
使っていた。`entry_to_invocation` が `actual_outcome` へ写すのは `agreed_at` と `modification_note` のみで、
評価日は保留合意の日付（2026-05-11）のまま、理由は `None` に落ちていた。**記録した本人が気づかず、
レビュー bot の指摘で発覚した**（PR #193 Copilot review）。同一サイクル内で同じ形の欠陥を 3 回踏んだことになる。
I-4「検出器は黙って捨てない」が、集計だけでなく**書式の不一致**にも及ぶべきことを示す実測である。

## F4. 人間駆動ループの表現（priority: standard）

v6.12.0 が Type C 献上として第 0 層へ差し戻した論点。GRAPH.yml は `type: loop` に `max_iterations` を
例外なく必須とするが、人間駆動ループ 2 本には上限値がどの規範にも宣言されていない。
F3-2（値の新規決定を行わない）と F1-4（例外なし）を同時に守る唯一の道が「書かないこと」だった。

| 条件 | 内容 |
|---|---|
| F4-1 | ループ終端の表現に `terminator: human` を追加する。`max_iterations` の**代替表現**であって緩和ではない（終端が回数ではなく人間の停止判断である、という事実の記述） |
| F4-2 | 適用対象は人間駆動ループ 2 本に限る ── (a) `layer0-spec-architect ⇄ human`（認識ズレゼロ化ループ）/ (b) `human-P3-事後評価 → human-P1-発案`（ハーネス自体が育つ戻り） |
| F4-3 | `execution_graph.py` の検査を「`max_iterations` **または** `terminator` のいずれか必須」に読み替える。両方欠落は従来どおり FAIL |
| F4-4 | AI 駆動ループへの `terminator: human` 適用は**禁止**。AI が回すループの上限を人間の停止判断に委ねることは、P4 介入権の事後発動化にあたる |

**なぜ回数で表さないか**: 人間駆動ループは AI 暴走のリスクを持たない（人間がいつでも止められる）。
上限回数を発明すれば F3-2「値の新規決定を行わない」に抵触し、書かなければ配線漏れとして残り続ける。
第三の道として、終端の性質そのものを記述する。

## モード判定・実装体制

- DH 本体の継続開発（LC ≥ 1）・**M2**（R ≥ 2 = 他人配布によりオーバーライド。L2 発動閾値はいずれも未超過）
- AI 能力バージョン: Claude Opus 5
- CTL: **CTL-0**。C カテゴリも全件人間献上
- **実装順序: F3 → F2 → F1 → F4 → F5**。I-3 により **F2 が F1 に先行することは必須**。
  F3 を最初に置くのは、本リリースの受け入れ確認そのものが事後評価の集計に依存するため
- 実装前ゲート: **Council 諮問 必須**（escalation-matrix「規範文書改変」行）
- 献上時ゲート: **人間判定**（Council の `final_decision` は常に null）
- **本仕様の実装 PR は opt-in 領域に該当する**（`.github/workflows/auto-merge.yml` の改修 + `.claude/skills/` 3 ファイル以上の改修）。
  実装 PR に `human-review-needed` を付与する（F2-5 の自己適用）。なお**本起草 PR 自身は形式上 opt-in 領域に該当しない**
  （`dh-upgrades/` と `history/` のみ）。それでも停止札を付けるのは、採否が人間の決定に属する起草物だからであり、
  境界の値を動かす要請ではない
